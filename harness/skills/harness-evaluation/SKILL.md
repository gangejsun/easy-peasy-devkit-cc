# Harness(Graph) Evaluation

자산 단위("무엇이 있는가")가 아니라 **경로 단위**("작업 1건이 어떤 노드를 밟고, 어디서
멈추고, 무엇을 남기는가")로 평가한다. 점수는 내지 않는다 — 산출물은 **결함 목록**이고,
그 자체가 개선 백로그다. 영역별 표는 판정의 **입력**이지 판정 단위가 아니다.

**이 스킬 하나로 전수 검사가 끝나야 한다.** Step 1이 기계 판정을 전부 수집하고, Step 2가
8축으로 판정하고, Step 3이 세는 자리(축 8행 · 영역별 요약 · 불확실성 지도)를 채운다.
요청 관점과 축의 대응은 `references/coverage-map.md`가 원장이다 — **축을 개편할 때만** 읽는다.

## 8축

**축 간 담당이 겹치면 결과가 애매해진다.** 각 축의 "만 본다"를 지킨다.

| 축 | 질문 | 기계 판정 (Step 1) | 모델 판단 (Step 2) |
| --- | --- | --- | --- |

**P5와 P6은 직교한다** — 비용이 싸도 중복일 수 있고, 비싸도 정당할 수 있다(security-check).
**P2·P7·P8도 직교한다** — P2는 차단력, P7은 경계 넘김, P8은 소비자가 겪는 경로.

### P6 세부 — 이미 있는 자산에게 다시 던지는 3-질문

`rules/harness-change.md`의 추가 전 3-질문은 **자산을 만들 때만** 걸린다. 존재하는 자산에게
그 질문을 다시 던지는 곳이 여기다. 없으면 하네스는 자라기만 한다.

| 항목 | 무엇을 보는가 |
| --- | --- |
| ① **과잉** | 지금도 필요한가 · 모델 향상으로 불필요해지지 않았는가 · 문서 1~3줄로 될 것을 스크립트로 만들지 않았는가 · 읽는 코드 없는 선언(설정 필드·죽은 검사) |
| ② **중복** | 역할이 겹치는 자산 쌍 — 커스텀 vs **네이티브**(`/code-review`·`/simplify`·`/security-review`·`skill-creator`·`/init`·`/run`·`/loop`) · 커스텀 vs 커스텀 · 같은 규범을 두 파일이 주장(정본/인용 미표시) |
| ③ **애매** | 산출이 행동으로 이어지는가 — **꺼지지 않는 경고** · 판정 불가를 차단으로 접음 · 두 검사가 같은 것을 셈 · 조치 문구 없는 실패 보고 · 규칙과 반대 방향의 경고(오탐을 "승격 후보"로) |

시점 스탬프("Claude Code 버전 · 모델 · 날짜")를 반드시 남긴다. **직전 스탬프가 30일 이내이고
그 이후 하네스 자산 커밋이 0건이면** P6-② 재조사를 생략한다 — 날짜만으로 생략하지 않는다
(v5 후 14일에 10버전이 출하됐다). **커스텀 폐기를 제안하려면 양쪽 본문을 실제로 열어**
커버 영역을 비교한다 — 네이티브의 존재는 중복의 증거이지 열등의 증거가 아니다.
비교 대상은 **훼손되지 않은 최선 버전**이어야 한다.

#### P6-②의 판정은 셋이다 — 대체 · 유지 · 합성

**다섯 관점을 모두 적고** 판정한다: 커버 영역(양쪽 본문을 연 뒤에만) · 발동 정확성(오탐·미탐
이력) · 유지비(우리가 고치는가 플랫폼이 고치는가) · 소비자 도달 · 모델 의존성.

| 판정 | 조건 | 적용 |
| --- | --- | --- |
| **네이티브로 대체** | 다섯 관점에서 네이티브가 동등 이상 | 커스텀 폐기(폐기 프로토콜). 남은 참조를 네이티브 호출로 바꾼다 |
| **커스텀 유지** | 네이티브가 못 다루는 영역이 실재 | 그 영역을 스킬 본문에 1~2줄로 남긴다 |
| **합성** | 관점별로 우열이 갈림 | **네이티브를 기반에 두고 커스텀의 고유 가치만 얇게 올린다** |

선례: `/security-review`(브랜치 diff)와 `security-review` 스킬(전수·CVE·시크릿·결제)은 커버가
갈려 둘 다 살았고, `receiving-code-review`는 지적을 *생성*하지 않고 *검증*하는 쪽으로 좁혔다.
**적용까지가 판정이다** — 판정마다 `eval-report → rule-promotion`(자산 교체·승격)과
`eval-report → skill-enhancer`(스킬 재설계) 중 어느 쪽으로 보내는지 적는다.

## 워크플로우

### Step 1: 기계 판정 수집 — 다시 세지 않는다

한 블록이다. 전부 돌리고 출력을 보관한다 — 이것이 8축의 「측정」 열이다.

```bash
# 이 스킬은 `epcc-harness` 플러그인 소속이라 CLAUDE_PLUGIN_ROOT 가 harness/ 를 가리킨다 —
# 평가 대상인 devkit 자산(scripts/·skills/·agents/)은 그 **한 단계 위**에 있다.
# 저장소 루트를 직접 구한다. 이 스킬은 하네스 소스 저장소 밖에서는 평가할 대상이 없다.
R="$(git rev-parse --show-toplevel 2>/dev/null)"
[ -n "$R" ] && [ -f "$R/scripts/doctor.sh" ] || { echo "하네스 소스 저장소가 아니다 — 평가 대상 없음(판정 불가)"; exit 2; }
bash "$R/scripts/doctor.sh" --all            # fast · self-test · graph · consumer · usage · lessons · inventory
bash "$R/scripts/doctor.sh" --usage --root <소비자 프로젝트>     # 소비자가 있을 때만
# 가이드 하네스 — 직전 리포트 이후 guides/·stack-guide-generator/ 커밋이 있을 때만 (--regress는 느리다)
bash "$R/skills/stack-guide-generator/scripts/guide-gate.sh" --regress
bash "$R/skills/stack-guide-generator/scripts/pack-smoke.sh" --self-test
# P1 — 라우팅 어휘 (심각도 등급표 문맥은 제외하고 해석)
grep -rn 'Small\|Medium\|Large' "$R"/skills/*/SKILL.md
# P3 — 반복 상한 (공유 파일 포함)
grep -rln '최대 [0-9]회\|1회 재' "$R"/skills/*/SKILL.md "$R"/skills/*/references/*.md
# P7 — 밖으로 나가는 노드 · 잔존물
grep -rln 'WebSearch\|WebFetch\|codex' "$R"/skills/*/SKILL.md "$R"/agents/*.md
ls "$R"/dev/handoff/ 2>/dev/null | wc -l
# P6 재조사 판정 · P8 배포 도달 — 직전 리포트 이후 자산 커밋 수 · 미커밋 자산 수
LAST=$(ls -t "$R"/dev/docs/harness-evaluation/v*.md 2>/dev/null | head -1)
git -C "$R" log --oneline --since="$(date -r "$LAST" '+%Y-%m-%dT%H:%M:%S')" -- skills agents rules hooks scripts templates | wc -l
git -C "$R" status --porcelain -- skills agents rules hooks scripts templates workflow.graph.json | wc -l
```

**반복 증거의 출처** (P6-①·P2-④가 이것을 요구한다):
`docs/lessons.md` · `docs/lessons-archive.md` · `.claude/.epcc/{hookrun,graph,skilluse}.log` ·
`dev/handoff/*.md` · `dev/docs/skill-review/*` · 소비자 프로젝트(`--root`).
**2회 이상 관측된 것만 개입 근거가 된다** — 1회는 가설이지 패턴이 아니다.

### Step 2: 8축 판정 + 결함 목록 + 재현

- 축마다 두 줄로 판정한다: `측정: <기계 출력 요약 — 미계측 항목을 반드시 명시>` /
  `판정: <충족|부분 충족|미달|미계측> — <근거>`
- 결함은 `ID | 심각도 | 파일:행 | 실패 시나리오 | 개입 지점 | 수정 방향 | 처리` 형식.
  심각도는 epcc-reviewer와 동일 어휘(Critical/Important/Suggestion). ID는 전회에서 이어 붙인다.
- **개입 지점**은 수정이 놓일 자리다: ①시작 브리핑(T0·session-brief) ②결정 시점
  (규칙 `paths:`·스킬 발동) ③행동 체크포인트(PreToolUse) ④사후 복구(Stop·PostToolUse·handoff).
- **실패 시나리오를 쓸 수 없으면 그 결함은 보고하지 않는다** — "~일 수 있다"는 추측이다.
- **grep·doctor·inventory에 걸리지 않은 문서를 읽으러 가지 않는다.** 전 문서 독해는 폐기된 방식이다.
- 전회 판정을 계승하지 않는다 — 반드시 현재 파일로 재확인한다.
- **위임(Explore 등) 보고의 결함 후보는 파일:행을 직접 열어 재확인한 것만 목록에 올린다** —
  v6·v7 연속으로 위임 보고 2건씩이 현재 파일과 어긋났다(스탬프 부재 주장 · 플랫폼 기본값 주장).
- **P2는 독해로 충족을 판정하지 않는다.** 차단 장치마다 **픽스처에 없는** 우회·오탐 케이스를 격리
  주입하고(아래 재현 절차 · Stop 게이트는 합성 transcript), 그 결과를 측정 열에 적는다 — v8이 코드를
  전부 읽고 충족을 냈는데 v9 주입에서 우회 3건·오탐 5건이 나왔고, v6 E-21도 픽스처가 초록인 채
  4개월을 살았다. 픽스처 통과는 「픽스처가 아는 것」의 증명이지 「우회가 없다」의 증명이 아니다.

**Critical은 재현으로만 확정한다.** 문서 독해만으로는 Important 이하다. 재현은 계측 로그를
오염시키지 않는다(`EPCC_STATE_DIR` 격리 — v5 E-13의 교훈). 재현 명령에 파괴 구문·시크릿이
들어가면 **살아있는 훅이 그 명령 자체를 막는다** — 케이스는 파일로 쓰고 실행한다.

```bash
jq -nc --arg c '<재현할 Bash 명령>' '{tool_name:"Bash",tool_input:{command:$c}}' > "$TMPDIR/case.json"
EPCC_STATE_DIR=$(mktemp -d) CLAUDE_PROJECT_DIR="$R" bash "$R/scripts/security-check.sh" < "$TMPDIR/case.json"; echo "exit=$?"
```

**부재를 주장하는 결함은 세 가지를 먼저 한다** — 두 오탐(v2 E-06 · v5 E-18)이 전부 관측 하나로
부재를 결론냈다: ①정책이 있을 자리(코드)를 연다 ②그 이벤트가 일어날 시간을 줬는지
`docs/platform-contract.md` §5.1 발화 빈도로 확인한다 ③실행 경로의 바이너리로 잰다(셸 래퍼 아님).

**영역별 요약**을 쓴다 — `--inventory`의 영역(스킬·규칙·훅·에이전트·가이드 팩·참조·템플릿·
프리셋·문서·검사 스크립트)마다 1행: `영역 | 인벤토리 수치 | 이번 결함 ID | 한 줄 판정`.
결함이 없는 영역도 행을 비우지 않는다 — "없음"은 판정이다.

### 판정 규율 — 억지로 찾지 않는다

이 스킬의 성과는 결함 수가 아니다. **8축 충족 · 결함 0건은 정당한 산출이다** — 그때는 그렇게
쓰고 끝낸다. 충족 판정에도 측정 열에 무엇을 봤는지 적는다 — 빈 충족은 미계측이다.

- 결함마다 **처리**를 정한다: `수리` · `보류(근거)` · **`수용`**(고치지 않는다 — 개입 비용·회귀
  위험이 결함 비용보다 크다). Suggestion의 기본 처리는 **기록**이다(epcc-reviewer와 같다).
  보고 문턱은 낮추지 않는다 — 「실패 시나리오 없으면 보고하지 않는다」는 그대로이고, 보고와
  수리를 가를 뿐이다.
- 「수축 제안 최소 1건 검토」는 **검토 의무이지 제안 의무가 아니다.** 없으면 "없음 + 근거".
- 검토가 개편안으로 부풀면 멈춘다 — 요청 범위 밖 발견은 한 줄 보고하고 목록에만 남긴다.
  `docs/lessons.md`의 scope(2026-09-09)·false-positive(2026-09-04)가 정확히 이 실패였고,
  v7은 Suggestion 4건까지 12/12를 같은 회차에 수리했다 — 결함 수가 성과로 읽히기 시작한 신호다.
- 「검토했으나 개입하지 않는 것」을 표로 남긴다: `대상 | 왜 개입하지 않는가`. 다음 회차가
  같은 자리를 다시 파지 않게 하는 것이 이 표의 값어치다.

### Step 3: 저장 + 전회 대비 + 되먹임

1. 형식: `assets/report-template.md`. 절을 빼지 않는다 — 세는 자리가 없으면 세지 않는다.
2. 버전: `ls dev/docs/harness-evaluation/`의 최대 vN에 +1 (**파일명이 원장이다**)
3. 저장: `dev/docs/harness-evaluation/v{N}.md` — 저장 시점이 곧 외부 변화 점검 스탬프다.
   `session-brief` 훅이 최신 리포트의 mtime으로 30일 경과를 계산해 다음 점검을 알린다.
4. 전회가 있으면 결함 증감(ID 단위 신규·해소·잔존)과 상주 비용 증감만 요약한다. 점수 추세는 없다.
5. **수축 제안을 최소 1건 검토한다** (검토이지 제안 의무가 아니다). 없으면 "없음 + 근거"를
   적는다 — 승격만 있고 수축이 없으면 하네스는 자라기만 한다.
6. **불확실성 지도**를 표로 쓴다: `항목 | 상태(계측됨·미계측·여기서 불가) | 왜 | 닫는 조건 |
   어디서(여기·소비자·플랫폼)`. 전회 미계측이 이번에 계측됐으면 그 행을 "종결"로 남긴다.
7. **되먹임**: 이번 회차가 오탐을 철회했거나 평가 자신의 판정 오류를 발견했으면 그 자리에서
   `docs/lessons.md`에 `[category: false-positive]` + `- 장치:` 줄로 기록한다(`eval-report → lessons`).
   수축이 같은 회차에 자산 diff로 끝났으면 `docs/lessons-archive.md`로 **물리 이동**한다.
