## 내용 품질 (모델 판단)

- **공통으로 잘함**: RLS 유일 보안 경계, service_role 금지, 싱글턴 클라이언트, Zod+DB 제약 이중화, 생성 타입, 컴포넌트 직접 쿼리 금지. 우려했던 "Server Actions가 SPA 가이드로 새는" 대형 누출은 **양쪽 모두 없었다** — 각색 능력 자체는 검증됨.
- **B만 잡은 심화 지식**: `getUser()`(서버 검증) vs `getSession()`(스토리지 신뢰) 구분 — A는 오히려 "세션 접근은 항상 getSession()"이라고 적어 민감 동작 기준으로는 **더 약한 지침**. 그 외 목록 쿼리 기본 1,000행 제한, Realtime 구독 cleanup, Storage 비공개 버킷+signed URL, 리다이렉트 URL 허용 목록, "정책 없는 RLS=전면 차단" 뉘앙스.
- **A의 exemplar 관성 결함**: `[Preset:]` 접두사(플러그인 스킬에만 맞는 특성 상속), 리소스 12개(원본 10개 형태 상속+확장), data-modeling을 리소스 사본으로 회귀(원본은 T1 카드 참조인데 각색 과정에서 되돌림 — 방금 폐기한 사본 배포 재도입), 스탬프 부재.
- **A의 강점**: 원본과의 문체·구성 연속성, PostgREST 에러 코드표 충실.

## 결론

1. **실패 모드가 예상과 달랐다.** exemplar 방식의 위험은 "내용 누출"(모델이 잘 방어함)이 아니라
   **맥락 관성** — 원본에는 맞고 생성물에는 틀린 특성(프리셋 게이팅·리소스 규모·배포 방식)을
   무비판적으로 상속하는 것. 이는 기계 검증으로만 잡힌다.
2. **규격서 방식이 파이프라인 적합성에서 압승** (설치 게이트 전항 통과 vs 4항 불합격),
   내용 심화도에서도 우세 — 각색 앵커가 없어 스택 지식을 새로 소환했기 때문으로 해석.
3. **현행 설계(규격서 우선 + 형식 한정 예시 참조 + 기계 검증 게이트) 유지가 타당.**
   A의 결함 4종이 전부 "형식 참조 방화벽"이 금지하는 상속 유형이라는 점이 방화벽의 실증 근거.
