# 가이드 생성 방식 A/B 실측 — exemplar 각색 vs 생성 규격서

- 날짜: 2026-08-20 · 대상: backend-guide 생성 (n=1, 지표적 실험 — 단정 아님)
- 대상 스택 (동일): React 18 + Vite SPA(SSR 없음) + Supabase BaaS (PostgreSQL · supabase-js v2 브라우저 직접 · Supabase Auth)
- **A안**: `nextjs-backend-guide/SKILL.md`만 읽고 각색 (규격서 접근 금지) → 269줄
- **B안**: `guide-skeleton.md` 생성 규격서만 읽고 지식으로 생성 (기존 가이드 접근 금지) → 256줄
- 두 에이전트는 격리 컨텍스트, 동일 스택 명세, 동일 출력 요건. 토큰 비용 유사 (36.7k vs 38.7k)

## 기계 채점 (규격서 검증 항목)

| 항목 | A (exemplar 각색) | B (규격서) |
| --- | --- | --- |

## 내용 품질 (모델 판단)

- **공통으로 잘함**: RLS 유일 보안 경계, service_role 금지, 싱글턴 클라이언트, Zod+DB 제약 이중화, 생성 타입, 컴포넌트 직접 쿼리 금지. 우려했던 "Server Actions가 SPA 가이드로 새는" 대형 누출은 **양쪽 모두 없었다** — 각색 능력 자체는 검증됨.
- **B만 잡은 심화 지식**: `getUser()`(서버 검증) vs `getSession()`(스토리지 신뢰) 구분 — A는 오히려 "세션 접근은 항상 getSession()"이라고 적어 민감 동작 기준으로는 **더 약한 지침**. 그 외 목록 쿼리 기본 1,000행 제한, Realtime 구독 cleanup, Storage 비공개 버킷+signed URL, 리다이렉트 URL 허용 목록, "정책 없는 RLS=전면 차단" 뉘앙스.
- **A의 exemplar 관성 결함**: `[Preset:]` 접두사(플러그인 스킬에만 맞는 특성 상속), 리소스 12개(원본 10개 형태 상속+확장), data-modeling을 리소스 사본으로 회귀(원본은 T1 카드 참조인데 각색 과정에서 되돌림 — 방금 폐기한 사본 배포 재도입), 스탬프 부재.
- **A의 강점**: 원본과의 문체·구성 연속성, PostgREST 에러 코드표 충실.

## 결론

1. **실패 모드가 예상과 달랐다.** exemplar 방식의 위험은 "내용 누출"(모델이 잘 방어함)이 아니라
   **맥락 관성** — 원본에는 맞고 생성물에는 틀린 특성(프리셋 게이팅·리소스 규모·배포 방식)을
   무비판적으로 상속하는 것. 이는 기계 검증으로만 잡힌다.
2. **규격서 방식이 파이프라인 적합성에서 압승** (설치 게이트 전항 통과 vs 4항 불합격),
   내용 심화도에서도 우세 — 각색 앵커가 없어 스택 지식을 새로 소환했기 때문으로 해석.
3. **현행 설계(규격서 우선 + 형식 한정 예시 참조 + 기계 검증 게이트) 유지가 타당.**
   A의 결함 4종이 전부 "형식 참조 방화벽"이 금지하는 상속 유형이라는 점이 방화벽의 실증 근거.

# 2부 — 규격서 생성본 vs 실전 검증 원본 (nextjs-frontend/backend-guide)

같은 날 추가 실험. B 방식(규격서만, 격리)으로 frontend-guide(React+Vite SPA, 251줄)를
추가 생성해, 플러그인의 실전 검증 원본 2종과 쌍대 비교했다.

## 계량 비교

| 축 | 원본 frontend (nextjs) | 생성 frontend (B) | 원본 backend (nextjs) | 생성 backend (B) |
| --- | --- | --- | --- | --- |
| SKILL.md | 290줄 | 251줄 | 227줄 | 256줄 |
| 리소스 | **10개 2,967줄 (실재)** | 6개 (계획만) | **10개 2,910줄 (실재)** | 5개 (계획만) |
| 원칙 good/bad 쌍 | 8개 중 2개만 쌍 | **7개 전부 쌍 + 실패 이유 주석** | 8개 중 1개만 쌍 | **7개 전부 쌍** |
| 규격 적합 | 규격의 도출 원천 (자연 일치) | 전항 일치 + 스탬프 | 동일 | 동일 |
| 실전 검증 | **앱 개발로 검증·승격 누적** (반복 UI 추출 등) | 미검증 | 동일 | 미검증 |

## 판정

- **허브(SKILL.md) 수준**: 생성본이 대등~우세. 원칙마다 좋/나쁨 쌍과 "왜 실패하는가" 주석이
  붙고, 원본에 없는 심화 지식을 담음 (frontend: useEffect fetch 금지·셀렉터 구독·쿼리 무효화·
  동적 클래스 금지·코드 분할 / backend: getUser vs getSession·1,000행 제한·구독 cleanup).
  원본 원칙 중 일부는 컨벤션 나열(function 키워드·alias·import 목록)로, 생성 code-conventions
  카드와 역할이 겹치는 층위였다.
- **전체 스킬 수준**: 원본이 명백 우위. 리소스 ~3,000줄의 실재 깊이 + 실사용에서 승격된
  규칙(공통 레이아웃 추출 등)은 신선 생성이 대체할 수 없는 자산이다.
- **규격서 계약의 작동 실증**: 규격서에 넣은 "frontend는 반복 UI 추출 필수" 조항이 생성본에서
  레이아웃 라우트(`<Outlet />`) 원칙으로 구현됨 — 규격 갱신이 생성 품질로 전이된다.

## 역이식 (비교가 원본을 개선함)

비교 과정에서 검출된 원본 결함을 즉시 수리:

1. **도메인 잔재 제거** — 원본 frontend 가이드의 SKILL.md·file-organization·routing-guide·
   complete-examples에 이전 앱의 도메인(딜/Deal·payment·toss)이 배포물에 그대로 남아 있었다
   → 전부 일반화 (posts/user/comment, 외부 연동 예시화)
2. **backend 원칙 8 추가** — 생성 실험이 발굴한 `getUser()`(서버 검증) vs `getSession()`(표시용)
   구분을 원본에 역이식

## 함의

- nextjs-supabase 조합에 원본을 계속 쓰는 현행 결정(중복 생성 금지)은 타당 — 근거는 리소스
  깊이와 검증 누적이지 허브 품질이 아니다.
- 생성 방식은 허브 품질 기준선을 충족한다. 리소스 생성 단계까지 실행되면 타 스택 소비자도
  준수한 출발선을 얻는다 (단, 검증 누적은 사용에서만 온다 — lessons 루프가 그 통로).
- 원본과 생성 체계는 일방향이 아니다: 원본→규격서(구조 도출·동기화 의무)와
  생성 실험→원본(역이식)의 **양방향 개선 루프**가 이번에 실증됐다.

## 후속 조치 (2026-08-21)

"전체 스킬 수준 원본 우위"의 두 근거를 분해한 재검토 결과:

- ② 검증 누적은 규격서로 도달 불가능한 축 (lessons 루프가 통로 — 프로세스 결함 아님)
- ① 리소스 격차는 절반이 실험 아티팩트(2부는 허브만 생성, 리소스 미생성 비교)였으나,
  **규격서의 리소스 층위 규격이 얇다는 실질 결함**도 확인 — 허브는 8섹션 규격표로
  촘촘한데 리소스는 개수·줄수·파일명 원칙뿐, *어떤 리소스가 있어야 하는지*가 부재

→ 원본 리소스 20종에서 스택 무관 슬롯을 도출해 규격서에 **리소스 슬롯 표**
(frontend/backend 필수 7+7, 커버리지 의무·병합 허용·공백 보고 규칙) 신설,
동기화 의무를 리소스 층위로 확장, 검증 체크리스트 7항(필수 슬롯 커버) 추가.
분량 강제는 채택하지 않음 — "빈 슬롯이 틀린 내용보다 낫다" 원칙이 슬롯 표보다 우선.
