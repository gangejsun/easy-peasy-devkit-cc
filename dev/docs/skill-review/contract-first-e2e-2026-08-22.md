# 계약 우선 생성 — 엔드투엔드 실측 (2026-08-22)

계획 `nextjs-joyful-petal.md`의 검증 5. 사전 제작본이 없는 조합으로 파이프라인을 한 바퀴
돌려 **감사 지적 건수를 직전 세션(55건)과 부류별로 비교**한다.

- 조합: `vanilla`(JS) × `gcp-serverless` — Cloud Run 컨테이너 + Express 5 + Firestore +
  Identity Platform. **정책 엔진이 "있지만 deny-all로 잠긴" 세 번째 상태**라 사전 제작 두 쌍
  (RLS 이중 방어 / 정책 엔진 없음) 어느 쪽 서술을 옮겨도 즉시 틀린다
- 파이프라인: Step 3-0 계약 파일 → Step 3-1 격리 생성 2개(병렬) → Step 4 게이트 + `--pair`

| 부류 | 직전(react-aws, 55건) | 이번(vanilla×gcp, 57건) | 판정 |

### A·B — 계약 우선 생성과 원장이 작동했다

B가 25 → 7로 무너졌다. 남은 7건은 전부 **원장의 사각지대**다:

| 살아남은 B | 왜 빠져나갔나 |
| --- | --- |
| `--button-pad` 유령 CSS 변수 | 원장이 JS export만 추적 |
| JSDoc `@typedef`의 파일 간 참조에 import 없음 | 원장이 JSDoc 타입을 심볼로 안 봄 |
| `src/db/cursor.ts` 선언만 있고 정의 없음 | 원장이 **파일 경로 선언**을 안 봄 |
| `firebase.json`·`tsconfig.json` 내용 부재(명령 3개가 전제) | 설정 파일이 원장 대상 아님 |
| `requireRole` import되나 미사용 | 미사용 import는 원장 검사 밖 |
| `noteCount` 필드가 모델링 없이 예제에만 | 필드는 원장 대상 아님 |
| 구조도 설명이 소유 심볼 3개 누락 | 산문 ↔ 원장 대조 없음 |

**원장 규율 자체는 유효했고 구멍은 적용 범위다.** 확장 대상이 구체적으로 드러났다.

### C — 계획의 예측이 빗나갔다

계획은 "계약 층이 먼저 고정되므로 파일 간 상충이 줄고, 완전 예제가 통합 검사가 된다"고
했다. **그렇게 되지 않았다.** 계약은 와이어 층(봉투·에러 코드·페이지네이션)만 고정했고,
실제로 어긋난 26건은 전부 **그 아래층**이다:

- 배포 명령 `--no-allow-unauthenticated` ↔ 9줄 뒤 "`--allow-unauthenticated`가 필요하다"
- 허브의 계층 규율("`db/`는 Express를 모른다") ↔ 정본 예제의 `db → http` 역방향 import
- 린트가 경계를 "강제한다"는 문장 ↔ `files`가 두 디렉토리로 한정된 config
- `env.js`가 부팅 throw ↔ `vitest.config.js`에 `test.env` 없음 (CI에서 전 테스트 실패)
- 산문 "동적 구간은 맵의 키를 접두사로" ↔ `routes[path] ?? routes['*']` 정확 일치
- 계약 §5 "401 재실패 → 로그인" ↔ 두 파일이 서로를 가리키며 구현 0건
- 스키마는 임의 DB ID 허용 ↔ 테스트 초기화는 `(default)` 하드코딩
- `SESSION_SIGNING_KEY`를 배포 명령이 주입 ↔ `EnvSchema`에 없음(같은 페이지가 금지한 것)

공통 구조: **정책을 선언한 곳과 그 정책을 구현·실행하는 곳이 다르고, 둘을 맞춰볼 의무가
없다.** 심볼은 원장이 강제했지만 정책에는 원장에 해당하는 장치가 없다.

### D — 늘어난 것이 아니라 더 잡힌 것이다

D가 9 → 20인데 이 증가분의 상당수는 **이번에 새로 넣은 검출 장치의 산물**이다:

- 감사 프롬프트의 **버전 주장 판정표**(축 6 삭제하고 넣은 것) → 백엔드 28행·프론트 20행
  전수 판정. TS 7의 `baseUrl` 제거, Express 5의 `req.body === undefined`,
  `res.send(404)`의 세대 오귀속이 여기서 나왔다
- **Step 4-1 스키마 실행** → `z.flattenError`가 `formErrors`를 버려 `details`가 빈 객체로
  나가는 것을 실행으로 확인. `.partial()`+`default()` 경고는 **참**으로 판정
- 감사자가 자발적으로 `tsc`·`express`·`firebase-admin`을 실제 설치해 실행 → `@/` 별칭이
  방출물에 그대로 남아 컨테이너가 부팅 실패, `*splat`이 루트 `/`를 매치 못 함

즉 D의 증가는 계획이 의도한 방향("D는 감사 영역으로 남기되 실행 가능한 부류만 실행으로
옮긴다")과 일치한다. **다만 이 때문에 55 vs 57 총량 비교는 성립하지 않는다.**

## 비교 가능성의 한계 (정직하게)

두 숫자는 엄밀히 비교되지 않는다:
1. 스택이 다르다(관리형 컨테이너+RDS ↔ 서버리스+NoSQL+두 종류 인증 경계)
2. **감사 프롬프트가 바뀌었다** — 축 6을 빼고 버전 주장 판정을 넣었으므로 D 검출력이 올랐다
3. 감사자가 다르다

**방법론적으로 신뢰할 수 있는 결론은 A·B뿐**이다. 그 둘은 생성 규율이 직접 겨냥한
부류이고 검출 장치는 그대로였다.

## 게이트가 이번에 드러낸 자기 결함 2건 (수리·커밋 완료)

사전 제작 4개 가이드로는 재현되지 않던 것들이다:

1. **미탐** — `(Bad|BAD)([^A-Za-z]|$)`가 `BAD_SHAPE`의 밑줄을 단어 경계로 인정해
   `// ✅ ... BAD_SHAPE ...` 주석이 안티패턴으로 판정됐다. 그 지점부터 코드 추출이 꺼져
   원장 대조·중복 정의·env 커버리지가 조용히 구간을 건너뛴다
2. **오탐** — `--forbid`가 부분 문자열 매칭이라 금지어 `next`가 계약 필드명 `nextCursor`에
   걸렸다. 같은 게이트의 `--pair`는 그 필드를 요구하므로 두 검사가 서로 반대를 요구했다

둘 다 `--self-test`에 음성 픽스처로 고정했고, 결함을 되돌린 사본으로 픽스처가 실제로
exit 1을 받는지 확인했다.

## 계약 양식의 구멍 — 도메인 어휘

프론트는 `/tasks`, 백엔드는 `/notes`를 쓴다. 같은 시스템을 설명하는 두 가이드가 서로 다른
리소스 이름을 쓴다. 계약이 봉투·코드·페이지네이션은 못박았지만 **예제의 도메인 어휘는
지정하지 않았다.** 사전 제작 react-aws 쌍도 정확히 같은 상태(`/tasks` ↔ `/notes`)이므로
우연이 아니라 양식의 구멍이다. `--pair`의 엔드포인트 차집합이 REVIEW로 잡아냈다.
