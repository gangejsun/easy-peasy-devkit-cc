  → 수리 → 재검증). 서브에이전트 6개, 메인 세션 독립 검증.

## 왜 만들었나

조직 표준 스택이라 기존 사전 제작 조건 — *"정기 감사 대상으로 등록할 수 있을 때만
사전 제작한다"* — 을 충족한다. 인터뷰에서 **PostgreSQL이 사내 온프레미스 인프라의 스택이고
향후 백엔드를 온프레미스로 되돌릴 수 있다**는 제약이 나와, 이식성이 아키텍처 선택과 가이드
내용의 중심축이 됐다.

## 확정 스택과 그 근거

React + Vite SPA × 컨테이너 API(Hono on ECS/Fargate) + RDS PostgreSQL + Drizzle +
Cognito(OIDC/JWKS). 서버리스 대신 컨테이너를 고른 이유 세 가지:

- **비용**: PostgreSQL을 쓰면 DB가 이미 상주 비용이라 Lambda의 scale-to-zero 이점이
  RDS Proxy + VPC 엔드포인트/NAT로 상당 부분 상쇄된다
- **AI Native**: `docker compose`로 Postgres까지 로컬 재현되어 에이전트가 마이그레이션·
  통합 테스트를 직접 실행해 자기 작업을 검증할 수 있다. Lambda는 이 루프가 끊긴다
- **이식성**: Lambda 핸들러는 AWS 고유 시그니처라 온프레미스 전환 시 재작성이 필요하다

가이드의 고유 축은 **이식 가능한 경계**다 — AWS 종속을 인프라 층에만 두고 앱 코드는
벤더 중립으로 유지하는 6개 계약(표준 HTTP 런타임 / Aurora 전용 기능 회피 / OIDC 표준
검증으로 Cognito SDK 미의존 / S3 엔드포인트 설정 가능 / stdout 구조화 JSON / env 단일
진입점)을 전용 리소스에 두고 다른 리소스의 예시가 이를 지키는지 감사에서 교차 검증했다.

## 프로세스 결함 발견 — 격리 생성이 조합 계약을 끊었다

**이번 작업의 가장 큰 소득은 산출물이 아니라 프로세스 결함의 발견이다.**

Step 3은 맥락 관성을 막으려고 두 가이드를 격리 생성한다. 그런데 그 탓에 **두 가이드가
와이어 계약을 합의할 방법이 없었고**, 결과는 이랬다:

| 항목 | 백엔드가 만든 것 | 프론트가 만든 것 |
| --- | --- | --- |
| 성공 봉투 | `{ data }` · `{ data, nextCursor }` | 봉투째 `as T` (벗기지 않음) |
| 에러 봉투 | `{ error: { code, message, details }, requestId }` | `payload.code`·`payload.message` (평평) |
| 페이지네이션 | 커서(`limit`/`cursor`→`nextCursor`), `total` 없음 | 오프셋(`page`/`total`/`items`) |
| 인가 실패 | **404**(존재 누설 금지) | 403 축으로만 서술 |

완전 예제와 422 폼 에러 흐름이 통째로 실행 불가였다. 한쪽만 읽는 감사로는 잡히지 않고,
**두 산출물을 나란히 놓아야만** 보인다.

→ 수리: `stack-guide-generator`에 **Step 3-0(와이어 계약 선확정)** 신설. 쌍으로 생성할 때는
메인 세션이 성공/에러 봉투·페이지네이션 모델·에러 코드 목록·인가 실패 표면 5항목을 먼저
정해 양쪽에 토씨까지 동일하게 전달한다. Step 4에 계약 정합 대조 명령도 추가.

## 감사가 잡은 것 (기계 게이트는 양쪽 다 통과한 뒤였다)

두 가이드 모두 기계 게이트 8종을 통과했다. 결함은 **전부 게이트가 못 보는 축**에 있었다.

**치명 — 메인 세션이 zod 4.4.3으로 실행 재현**

`UpdateNoteInput = CreateNoteInput.partial()`인데 `body: z.string().default('')`의 기본값이
살아남아:

```
수리 전: {} → {"body":""} (가드 통과)   ·  {title:"x"} → {"title":"x","body":""}
수리 후: {} → REJECTED                 ·  {title:"x"} → {"title":"x"}
```

서비스가 `set({ ...patch })`를 하므로 **제목만 고치는 PATCH가 본문을 지웠다.** 대표 예제이자
두 파일에 복제돼 있어 그대로 설치되면 사용자 데이터가 조용히 사라진다.

**보안 기능이 정의만 있고 미적용** — 프론트의 `AuthWiring`(토큰 주입), `safeReturnTo`
(오픈 리다이렉트 방어), `/auth/callback` 라우트가 각각 정의 1건·호출 0건이었다. 배선이
없으면 방어 코드는 장식이다. 백엔드도 `signState`·`authRoutes`가 미정의였고, 로그인 URL
라우트를 `requireAuth` 아래 붙이면 **로그인하려면 먼저 로그인해야 하는** 데드락이었다.

**지침이 정반대** — 백엔드 안티패턴 카드가 헬스체크 미들웨어 순서를 거꾸로 가르쳤다
(Hono는 등록 순서대로 실행하므로 `/healthz` **뒤**가 안전한데 "뒤에 두면 죽는다"고 적혀
있었다). 프론트는 `size-4`를 "v4 전용"이라 했는데 실제로는 Tailwind v3.4에 추가됐다.

전체 수리: frontend 28건, backend 27건(+ 운영/배포 리소스 1개 신설).

## 한계 — 정직하게

기존 nextjs 쌍의 강점인 **실사용에서 승격된 규칙**은 이 세트에 없다. 참조 프로젝트가 없는
신규 표준이기 때문이다. 이식 가능한 경계와 정책 엔진 부재 하의 소유권 규율은 *설계에서*
나오는 강한 축이라 공백을 상당 부분 메우지만, 실전 검증은 사용에서만 온다 —
`docs/lessons.md` 루프가 그 통로다.

사전 제작본이 2쌍이 되어 **정기 감사 대상도 2배**다. 기준선 선언(`epcc-guide-baseline`)과
감사 재실행 절차가 실제로 돌아야 이 결정이 정당화된다.
