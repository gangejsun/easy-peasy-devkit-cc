## 이번 작업이 드러낸 것

### 1. 네 가이드가 서로 다른 시스템을 설명하고 있었다

프론트는 `task`(217회), 백엔드는 `note`(166회). 한글도 `작업` ↔ `노트`로 갈렸다.
두 쌍 모두 그랬으므로 우연이 아니라 **계약 양식의 구멍**이다 — 봉투·코드·페이지네이션은
못박았지만 도메인 어휘를 지정하지 않았다. 계약 템플릿에 `§0 도메인 어휘`를 넣고
게이트가 대조하게 했다. 개명 169곳 + 조사 교정.

### 2. 팩에는 두 형태가 있다

| 형태 | 예 | export |
| --- | --- | --- |
| 심볼 표면형 | `aws-container` (5리소스 1,191줄) | 25개 |
| 패턴 지식형 | `supabase` (2리소스 380줄) | **0개** |

BaaS 축이 얇은 것은 결함이 아니다 — 그 조합의 "백엔드 가이드"는 대부분 호스트 런타임
관심사이고 그것은 프론트엔드 축이 정한다. 게이트가 `symbolSurface: false`를 읽어
원장 역방향 검사를 건너뛰게 했다.

### 3. `nextjs-backend-guide`는 Supabase 팩이 아니었다

"Next.js가 호스팅하는 Supabase 백엔드"라 검증·에러·엣지 파일이 **문단 단위로** 얽혀
절 경계로 갈리지 않았다. 계획의 재조정 조건에 걸려 **깨끗이 갈라지는 것만 팩으로 보내고
나머지는 이음매가 흡수**하게 했다 (이음매 7파일). 그 결과 supabase 팩이 얇아졌고,
그것이 위 §2의 발견으로 이어졌다.

### 4. 계약은 기계가 읽는 문서다

`--pair`가 처음에 14건을 오인했다. 원인은 전부 **설명 산문 속 백틱**이었다:
"실측에서 백엔드가 `/notes`를 썼다"가 계약 요구사항으로 둔갑했다. 값은 목록·표 행에만
쓰고 산문·인용문은 설명으로 취급하도록 바꿨다.

### 5. 경계가 항상 HTTP인 것은 아니다

`nextjs × supabase`는 프론트가 자기 REST를 부르지 않는다 — 서버 컴포넌트가 데이터
계층을 직접 읽고 변이는 Server Action으로 간다. HTTP 계약을 양쪽에 요구하면 **정상
조합이 영구 FAIL**이 된다. 계약 절마다 `> surface: frontend|backend`를 선언할 수 있게
했다. 이 과정에서 `totalPages`가 와이어 필드가 아니라 프론트 파생값이라는 것도 드러났다.

### 6. 게이트가 자기 결함 4건을 드러냈다

| 결함 | 증상 |
| --- | --- |
| 예외 파일 열 미적용 | 공백 하나 때문에 모든 예외가 무시됨 |
| 이스케이프 파이프 절단 | `await (params\|...)` 정규식이 `await (params\`로 잘림 |
| `PGRST116` → `116` | 상태 코드 추출이 식별자 안의 숫자를 잡음 |
| 배송 스탬프가 예산 초과 유발 | 정확히 300줄인 원본이 팩으로 옮겨지는 것만으로 301줄 |

전부 `--self-test` 픽스처로 고정했다.
