# Presets Guide

프리셋은 **프론트엔드 축과 백엔드 축 두 개**로 나뉜다. `/epcc-init`에서 각각 하나씩 고르면
스택 조합이 확정되고, 그 조합에 맞는 가이드 스킬이 결정된다.

> **왜 2축인가**: 가이드 내용은 한 축의 함수가 아니라 **조합의 함수**이기 때문이다.
> 같은 Supabase라도 Next.js와 짝지으면 Route Handlers·Server Actions 중심이고,
> React+Vite SPA와 짝지으면 Edge Functions·브라우저 직접 호출 중심으로 완전히 다른
> 가이드가 된다. 두 축을 먼저 확정해야 서로를 고려한 가이드를 만들 수 있다.

## 프론트엔드 축 (`presets/frontend/`)

| 이름 | 스택 | 서버 코드 위치 |
| --- | --- | --- |
| `nextjs` | Next.js 15 App Router + React 19 + Tailwind v4 + shadcn/ui + Zustand | 프레임워크 내장 (Route Handlers·Server Actions) |
| `react-vite` | React + Vite SPA (SSR 없음) + Tailwind + React Router + Zustand | 없음 — 백엔드 축이 전적으로 소유 |
| `vue` | Vue 3 Composition API + Vite SPA (SSR 없음) + Tailwind + Vue Router + Pinia | 없음 — 백엔드 축이 전적으로 소유 |
| `vanilla` | 프레임워크 없음 — 표준 DOM + ES 모듈 (Vite 번들) | 없음 |
| `none` | 프론트엔드 없음 (API 전용 프로젝트) | — |

**언어는 프리셋이 아니라 차원이다.** 모든 프론트엔드 프리셋은 TypeScript를 기본값으로
두되(`vanilla`만 JavaScript 기본), `/epcc-init` Step 4에서 바꿀 수 있다. JavaScript를 고르면
가이드의 타입 표준 슬롯이 JSDoc 규약과 런타임 스키마 검증으로 대체되고 생성 타입 절은 빠진다.

## 제품 형태도 차원이다 (`techStack.deliveryModel`)

`/epcc-init`이 **가장 먼저 묻는 것**은 프레임워크가 아니라 **무엇을 만드는가**다 —
웹 · 하이브리드 앱 · 네이티브 계열 · API 전용. 답하려면 이미 알아야 하는 기술 질문 대신
누구나 답할 수 있는 제품 질문을 먼저 두고, 그 답이 뒤 질문의 목록을 좁힌다.

| 값 | 뜻 | 프론트엔드 축 |
| --- | --- | --- |
| `web` | 브라우저로 접속. `pwa: true`면 설치형 | 4종 전부 |
| `hybrid` | 하나의 웹 코드로 웹과 스토어 앱을 함께 (Capacitor 등) | 4종 전부. **단 `nextjs`는 정적 내보내기 강제** |
| `native` | React Native · Flutter · Swift · Kotlin | **대응 축 팩 없음** — `nativeStack`을 입력으로 생성 |
| `api-only` | 사용자 화면 없음 | `none` |

**축이 아니라 차원인 이유** — 팩을 늘리지 않고 **기존 팩의 조건부 슬롯을 켜고 끄기**
때문이다. 축으로 만들면 사전 제작 대상이 곱집합으로 늘어 감사 가능한 수를 넘는다.

파생값 **`clientKind`**(`web`이면 `browser`, 나머지 셋은 `app`)가 백엔드 가이드를 가른다.
하이브리드·네이티브는 백엔드 입장에서 전부 같기 때문이다 — "브라우저가 서버와 대화"가
아니라 **"앱이 API와 대화"**다.

| 슬롯 | `browser` | `app` |
| --- | --- | --- |
| 클라이언트 인증 전달 | 쿠키 세션 · CORS · CSRF | Bearer + 보안 저장소 |
| 멱등 수집 | 빈다 | 살아난다 (오프라인 배치 동기화) |
| 푸시 발송 | 빈다 | 살아난다 (FCM/APNs) |
| API 버전 협상 | 빈다 | 살아난다 (구버전 앱이 계속 돈다) |

**슬롯이 비는 것은 정상 경로다.** 웹 프로젝트의 백엔드 가이드에 푸시 절이 없는 것은 결함이
아니라 차원이 작동한 결과다. 그래서 **팩은 어떤 차원 조합에도 성립해야 하고 특화는 생성
시점에 일어난다** — 차원별 내용을 팩에 박으면 나머지 조합에서 틀린 지침이 된다.

## 백엔드 축 (`presets/backend/`)

백엔드는 **형태가 세 가지**다 — 이름만 다른 동급 항목이 아니다.

| 이름 | 형태 | 스택 | 보안 경계 |
| --- | --- | --- | --- |
| `supabase` | BaaS | PostgreSQL + RLS + Auth + Storage + Realtime | RLS가 최종 방어선. 정책이 없으면 **전면 차단** |
| `firebase` | BaaS | Firestore + Auth + Storage + Cloud Functions | Security Rules가 최종 방어선. 규칙이 없으면 **전면 개방**(RLS와 정반대) |
| `aws-serverless` | 서버리스 조립 | Lambda + API Gateway + DynamoDB + Cognito | **행 수준 정책 엔진 없음** — 애플리케이션 층 검사가 실질적 유일 경계 |
| `aws-container` | 자체 서버 | ECS/Fargate + ALB + RDS PostgreSQL + Drizzle + Cognito(OIDC) | **행 수준 정책 엔진 없음** — 소유권 검사 누락이 곧 데이터 유출. AWS 종속을 인프라 층에만 두어 온프레미스 이식이 가능하다 |
| `gcp-serverless` | 서버리스 조립 | Cloud Run/Functions + Firestore + Identity Platform | IAM/토큰 검증 + (직접 접근 경로가 있으면) Security Rules |
| `fastapi` | 자체 서버 | **Python** · FastAPI + SQLAlchemy 2.0 + Pydantic v2 + Alembic + pytest | 애플리케이션 층이 유일한 경계 |
| `node-api` | 자체 서버 | Express 5 + PostgreSQL + Prisma + Zod | 애플리케이션 층이 유일한 경계 |
| `node-nest` | 자체 서버 | NestJS 11 + PostgreSQL + TypeORM 1 + class-validator | 애플리케이션 층이 유일한 경계. `where`가 **배열이면 OR**라 분기마다 소유권을 반복해야 한다 |
| `none` | — | 백엔드 없음 / 외부 REST API 소비 | 외부 API 토큰 보관 위치가 위험 지점 |

**데이터 계층에 정책 엔진이 있는지가 가이드 내용을 가장 크게 가른다.** 있으면 애플리케이션
검사를 이중 방어로 쓰지만, 없으면 소유권 검사 누락이 곧 데이터 유출이다. 두 서술을 뒤바꾸면
안전하다는 착각을 만들기 때문에 생성 시 이 값을 반드시 전달한다.

`frontend: none` + `backend: none`은 이전의 `blank` 프리셋에 해당한다.

## 조합 → 가이드 매핑 — 사전 제작 단위는 축이다

조합은 5×9 = **45가지**지만 축은 **14가지**(프론트 5 · 백엔드 9)다. 그리고 가이드 내용의
대부분은 조합이 아니라 **한 축만의 함수**다 — 백엔드가 Supabase든 AWS든 React 컴포넌트
패턴과 스타일링은 같다. 그래서 사전 제작 단위를 조합이 아니라 축으로 둔다.

```
guides/
  frontend/<축>/   PACK.md · resources/ · ledger.md · policies.md · pack.json
  backend/<축>/    (같음)
  seams/<조합>/    조합에 진짜 의존하는 부분만 — 데이터 페칭 · 인증 · 완전 예제
```

프로젝트에는 둘을 조립해 `.claude/skills/frontend-guide`·`backend-guide`로 설치한다:

```bash
bash "${CLAUDE_PLUGIN_ROOT}/scripts/install-guide.sh" \
  --frontend <팩> --backend <팩> [--seam <조합>]
```

| 상태 | 동작 | 소요 |
| --- | --- | --- |
| 두 축 팩 + 사전 제작 이음매 | 조립만 — init 안에서 완결 | 초 단위 |
| 두 축 팩 · 이음매 없음 | 팩 조립 + 이음매만 생성 (축당 3파일) | init은 즉시 종료 |
| 한 축만 팩 | 그 축은 조립, 반대 축은 전체 생성 | init은 즉시 종료 |
| 팩 없음 | 양쪽 전체 생성 | init은 즉시 종료 |
| `none` × `none` | 없음 (Core 스킬만) | — |

현재 보유한 축 팩은 **프론트 4개**(`nextjs` · `react-vite` · `vue` · `vanilla`)와
**백엔드 8개**(`supabase` · `firebase` · `aws-serverless` · `aws-container` ·
`gcp-serverless` · `fastapi` · `node-api` · `node-nest`)이고, 사전 제작 이음매는 3쌍이다.
이 12개로 45가지 선택지 중 **44가지가 적어도 한 축을 완성품으로** 받는다 —
아무것도 받지 않는 것은 `none` × `none` 하나뿐이다.

**init은 가이드를 기다리지 않는다.** 생성이 필요하면 `.epcc/guide-job.json`에 작업을
남기고 끝나며, 완성·감사·수리를 마친 뒤에만 설치한다 — 미완성 반쪽 가이드는 깔지 않는다.
세션이 끊기면 다음 세션의 브리핑이 미완 작업을 알린다.

> 근거: 생성 1회의 실측이 **수리 전 54분**이었고 그 끝에서도 감사자 둘 다 설치 불가
> 판정을 냈다(`dev/docs/skill-review/contract-first-e2e-2026-08-22.md`). 설치 첫인상을
> 그 시간에 묶을 이유가 없다 — 가이드는 첫 컴포넌트를 쓸 때 필요하지 init이 끝나는
> 순간 필요한 것이 아니다.

**사전 제작본을 쓸지 생성할지는 시스템이 정한다 — 묻지 않는다.** 구현 세부가 사용자에게
새어 나가면 답할 수 없는 질문이 되기 때문이다. 다만 **지금 20분을 쓸지**는 사용자의
시간에 대한 결정이라 그것만 묻는다.

### 이음매 캐시 — 조합당 한 번만 만든다

이음매는 조합 1개에만 쓰이고 **양쪽 축 메이저 버전에 모두 부패**하므로(팩의 약 2배)
사전 제작 대상으로는 경제성이 낮다. 대신 캐시한다:

```
~/.claude/epcc/seam-cache/<조합>@<플러그인버전>/{frontend,backend}/
```

생성 → 게이트 → 감사 → 수리를 마친 뒤 `install-guide.sh --save-seam <조합>`으로 넣는다.
같은 조합의 **두 번째 프로젝트부터는 생성 없이 조립 1초**다. 캐시 항목은 나중에
사전 제작 이음매로 승격할 후보이기도 하다.

두 가지를 지킨다:
- **검증 통과분만 넣는다.** 미검증 산출물을 넣으면 그 조합의 모든 후속 프로젝트가 같은
  결함을 물려받는다 — 캐시가 결함의 증폭기가 된다
- **팩 소유 파일은 캐시에 넣지 않는다.** 넣으면 플러그인의 팩 갱신이 캐시에 가려
  영영 도달하지 않는다

### 갱신 도달 — 단, 스택 전제는 프로젝트가 고정한다

설치기는 스탬프 기반 멱등 갱신을 하지만 **아무도 다시 호출하지 않는다** — `epcc-init`과
`epcc-migrate`에서만 불린다. 그래서 플러그인을 올려도 오래 전 설치한 프로젝트는 옛 사본을
그대로 쓴다. 그런데 "무조건 최신으로"도 틀리다:

> **프로젝트는 시작 시점의 스택 전제 위에 코드를 쌓는다.** 플러그인 팩이 `next@16` 패턴으로
> 옮겼는데 이 프로젝트가 15라면, 갱신본은 낡은 것이 아니라 **이 프로젝트에 대해 틀린**
> 지침이다. 버전 상승은 의존성을 올릴 때 함께 하는 프로젝트의 결정이다.

그래서 **고정하는 것은 "스택 전제"이지 "지침의 정확성"이 아니다.** 판정은 팩 스탬프의
`pkgs=<패키지>@<메이저>`로 한다:

| 상태 | 동작 |
| --- | --- |
| pkgs 메이저 동일 · 팩 버전 상승 | **갱신한다** — 같은 전제 안의 결함·보안 수정이다 |
| pkgs 메이저 상이 | **갱신하지 않는다** — 전제가 이동했다. 프로젝트가 결정한다 |

앞줄이 실재한다는 근거: 사전 제작 가이드에 권한 상승 취약점이 몇 달간 있었다. 그건 버전
문제가 아니라 결함이었고, 같은 스택을 쓰는 프로젝트에 도달하지 않으면 안 된다.

이 정책은 두 곳에서 함께 작동한다 — 메시지로만 두면 강제되지 않기 때문이다:

- `session-brief`가 매 세션 대조해 **어긋날 때만** 알린다 (수정본은 재실행 안내, 전제
  이동은 "갱신하지 않습니다"라고 명시)
- `install-guide.sh`가 메이저가 다르면 **팩을 건드리지 않고 반환한다.** 알고 넘기려면 `--force`

T1 규칙 카드는 스택 전제가 없다(코드 변경 규율·되돌림·교훈)이므로 이 게이트 없이 항상
최신이 옳다.

### 팩에는 두 형태가 있다

| 형태 | 예 | 특징 |
| --- | --- | --- |
| 심볼 표면형 | `backend/aws-container`(5리소스 1,191줄) · 프론트 팩 | 프로젝트 모듈을 정의한다. 이음매가 import한다 |
| 패턴 지식형 | `backend/supabase`(2리소스 380줄) | 벤더 SDK를 **어떻게 쓰는가**를 가르친다. 정의하는 모듈이 없다 |

BaaS 축이 얇은 것은 자연스럽다 — 그 조합의 "백엔드 가이드"는 대부분 호스트 런타임
(핸들러·미들웨어·에러 봉투)에 관한 것이고 그건 프론트엔드 축이 정하기 때문이다.

### 팩 경계는 기계가 지킨다

갈라 배송하면 두 결함 부류가 새로 생긴다. 게이트가 둘 다 검사한다:

| 검사 | 잡는 것 | 근거 파일 |
| --- | --- | --- |
| 팩 인터페이스 | 팩이 소비하는데 이음매가 정의하지 않는 심볼 | `ledger.md`의 `requires` |
| 정책 원장 | 팩이 선언한 파일 간 불변식을 이음매가 어김 | `policies.md` |

두 번째가 특히 중요하다 — 실측 감사 57건 중 **26건**이 "정책을 선언한 곳과 강제하는
곳이 다르고 둘을 맞춰볼 의무가 없다"는 부류였다. 심볼에는 원장이 있었으나 정책에는
대응 장치가 없었다.

### 사전 제작 대상을 늘리는 기준

조합 단위로 전부 사전 제작하면 가이드 **45개(약 9만 줄)** 가 된다. 실측 근거가 있다:
가이드 2개에 권한 상승 취약점·폐기 API·이전 메이저 버전 잔재가 쌓여 **몇 달간 발견되지
않았고**, 그것을 찾는 데 감사 에이전트 3개와 수리 에이전트 2개가 들었다. 감사받지 않는
사전 제작본은 부패해서 **없는 가이드보다 나쁘다** — 틀린 지침을 신뢰하게 만들기 때문이다.

그래서 기준은 개수가 아니라 조건이다: **정기 감사 대상으로 등록할 수 있을 때만 사전
제작한다.** 축 단위는 이 조건을 충족한다 — 12개는 감사 가능한 수이고, 프론트 팩 하나를
감사하면 그것이 들어가는 조합 9가지가, 백엔드 팩 하나면 5가지가 함께 좋아진다.

### 구식화 점검 — 묻지 않고 대조한다

축 팩과 이음매는 파일 첫머리에 검증 기준선을 선언한다:


`/epcc-init`이 프로젝트의 `package.json`과 **메이저 버전을 대조**해, 어긋날 때만 어떤
패키지가 어떻게 다른지 보고한다. 일치하면 아무 말도 하지 않는다. "재생성할까요?"를 묻지
않는 이유는 사용자가 가이드의 낡음을 판단할 근거가 없어 그 질문이 곧 소음이 되기 때문이다.

## 병합 규칙

`/epcc-init`은 세 파일을 이 순서로 병합한다 (뒤가 앞을 덮어씀):

1. `presets/base.json` — 공통 `domains`
2. `presets/frontend/<선택>.json`
3. `presets/backend/<선택>.json`

- `additionalStack`은 덮어쓰지 않고 **누적**한다
- `domains.sourceDir`은 프론트엔드 축 우선, 프론트엔드가 `none`이면 백엔드 축
- 각 프리셋의 `notes`는 config에 기록하지 않고 **가이드 생성 에이전트에 조합 맥락으로 전달**한다

## 툴체인이 둘인 조합

`react-vite` × `fastapi`처럼 언어·패키지 매니저가 다른 조합은 축마다 명령이 다르다.
config는 이를 축별로 기록하되, **프로젝트 대표 명령**(`techStack.commands`)을 반드시 채운다 —
`build-gate`와 `health-check`가 읽는 값이다.

## 커스텀 스택

프리셋에 없는 조합은 `/epcc-init`에서 가장 가까운 축을 고른 뒤 Step 4.5에서 차원을 바꾸거나,
`/stack-guide-generator`를 직접 호출해 차원을 지정한다. 어느 쪽이든 같은 검증 루프를 거쳐
프로젝트 소유 가이드가 생성된다.
