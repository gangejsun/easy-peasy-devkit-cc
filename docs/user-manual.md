# 사용자 매뉴얼 — 무엇을 언제 어떻게 쓰는가

설치는 [Getting Started](getting-started.md)가, 설정 옵션은 [Configuration](configuration.md)이
담당합니다. **이 문서는 설치가 끝난 뒤 "그래서 실제 작업을 어떻게 하는가"**에 답합니다.

각 장치가 **왜** 그렇게 생겼는지 궁금하면 [하네스 해부](harness-anatomy.md)로,
하네스를 고치거나 운영하려면 [운영 매뉴얼](operations-manual.md)로 가세요.

---

## 1. 30초 개념 — 이 하네스가 하는 일 세 가지

Claude Code에 이 플러그인을 설치하면 세 가지가 생깁니다. **셋은 서로 직교합니다** —
따로 작동하고, 하나가 다른 하나를 대신하지 않습니다.

| # | 하는 일 | 무엇이 정하나 | 사용자가 느끼는 것 |
| --- | --- | --- | --- |
| ① | **무엇을 어떤 순서로** 만들지 라우팅 | 작업 유형 (신규/수정/버그/리팩토링) | Claude가 기획→PRD→구현 순서를 알아서 잡는다 |
| ② | **얼마나 검증할지** 강도 결정 | 되돌림 클래스 (건드리는 **경로**) | 마이그레이션을 만지면 리뷰가 붙고, 테스트 코드는 바로 진행된다 |
| ③ | **위험한 것 차단** | 훅 5종 (실시간) | 시크릿 하드코딩·`DROP TABLE`이 실행 전에 막힌다 |

**①과 ②는 곱해집니다.** "신규 기능"이면서 "마이그레이션을 건드림"이면 P0~P5 전 과정을
밟으면서 리뷰까지 붙습니다. "버그 수정"이면서 "테스트 파일만 고침"이면 바로 구현합니다.

> **한 문장 요약** — 규모(줄 수·파일 수)가 아니라 **경로와 작업 유형**이 절차를 정합니다.
> 300줄짜리 CSS 수정은 가볍고, 3줄짜리 마이그레이션은 무겁습니다.

## 2. 먼저: 내 작업은 어느 유형인가

Claude가 자동으로 판정하지만, **알고 있으면 대화가 훨씬 빨라집니다.**

| 내 상황 | 유형 | Phase 순서 |
| --- | --- | --- |
| 없던 기능을 새로 만든다, PRD도 없다 | 신규 기능 | P0 → P1 → P2 → P3 → P4 → P5 |
| 없던 기능인데 PRD는 이미 있다 | 신규 기능(PRD 有) | P3 → P4 → P5 |
| 있는 기능을 고치거나 확장하거나 지운다 | 수정 | **P4 → P5** |
| 버그를 잡는다 | 버그 수정 | **P4 → P5** |
| 동작은 그대로 두고 구조만 바꾼다 | 리팩토링 | P3 → P4 → P5 |
| 문서를 쓴다, 환경을 만진다, 그냥 알아본다 | 미적용 | 절차 없음 |

**Phase 번호는 순서 표시일 뿐 의무가 아닙니다.** 아래 네 가지가 이미 충족되면 Claude는
P0~P3을 통째로 건너뛰고 바로 구현에 들어갑니다.

> ① 의도 명확 · ② 컨텍스트 최신 · ③ 영향 반경 파악 · ④ 검증 경로 존재

**이 중 ①만은 사용자에게 있습니다.** 나머지 셋은 Claude가 스스로 채울 수 있지만, "무엇을
원하는가"는 물어볼 수밖에 없습니다. 그래서 **의도가 모호하면 개수와 무관하게 질문이 옵니다.**

> 💡 **질문을 줄이는 법** — 요청에 ⓐ 무엇을 ⓑ 왜 ⓒ 어디쯤에 를 한 줄씩 넣으세요.
> "로그인 고쳐줘"보다 "소셜 로그인 후 리다이렉트가 홈으로 안 가는 버그, `app/auth/`쯤"이
> 훨씬 빠릅니다.

## 3. 되돌림 클래스 — 내 변경은 얼마나 위험한가

**경로로 판정합니다. 규모로 판단하지 않습니다.**

| 클래스 | 어떤 경로 | 무슨 일이 일어나나 |
| --- | --- | --- |
| 🔴 **Irreversible** | `migrations/` · auth/RLS · 결제·정산 · 운영 데이터 | 다관점 독립 검증 + **사용자 확인 요청** + 롤백 절차 작성 |
| 🟡 **Costly** | 공유 패키지 · public API · 타입 계약 · `api/` · `actions.ts` · `middleware.ts` · 생성 파일 | `epcc-reviewer`가 diff를 독립 리뷰 — **자기 리뷰로 대체 안 됨** |
| 🟢 **Reversible** | 그 외 전부 (테스트 코드 포함, 기본값) | 바로 진행. 마무리는 `/completion-review` |

**왜 이렇게 하나** — 되돌릴 수 있는 실수는 싸고, 되돌릴 수 없는 실수는 비쌉니다. 검증
비용을 후자에 몰아주려는 것입니다. 모든 변경에 리뷰를 붙이면 아무도 그 리뷰를 안 읽게 됩니다.

> ⚠️ 🔴에서 **사용자 확인이 오면 그것은 형식이 아닙니다.** 그 시점이 되돌리기 가장 싼
> 마지막 지점입니다.

## 4. 작업 유형별 여정 (Use Case)

### 🅰 신규 기능 — UI가 있는 제품 기능

*예: "환자 예약 화면 3개를 새로 만든다"*

가장 긴 경로입니다. **각 단계는 "종료 술어"를 만족해야 다음으로 넘어갑니다** — 문서를
만들었다가 아니라 무엇이 확정됐는가로 판정합니다.

#### 기획 국면

| 단계 | 무엇을 | 언제 발동 | 끝났다는 신호 |
| --- | --- | --- | --- |
| **P0-A** `/brainstorming` | 아이디어를 설계로 | 요구사항이 한 문장으로 안 나올 때 | 한 문장으로 말할 수 있게 됨 |
| **P0-B** `/research` | 웹 기반 조사 | 외부 사실 확인이 필요할 때 | `dev/docs/research/`에 문서 |
| **P0-C** `/business-planner` | 수익 모델·시장 진입 | 사업성 판단이 필요할 때 | `dev/docs/business/` |
| **P0-D** `/service-planner` | **화면 목록·사용자 플로우** | 화면·플로우가 미확정일 때 | `dev/docs/service/service-plan-<name>.md` |
| **P0-E** `/council-review` | 기술·비즈니스·UX 3관점 | 되돌리기 어려운 **기획** 결정 | 통합 권고 + 사용자 선택 |
| **P2** `/prd-generator` | PRD 작성 | `dev/docs/prd/`에 없을 때 | PRD가 화면 목록을 수용 |
| **P3** `/dev-docs-generator` | plan·context·tasks | 작업이 **세션을 넘어갈 때만** | `dev/active/` 3종 |

> 💡 **P0-D의 산출물이 디자인의 입력이 됩니다.** 화면 목록을 여기서 확정해두면 다음
> 국면이 그것을 그대로 읽습니다. 건너뛰면 디자인 단계에서 다시 묻게 됩니다.

#### 디자인 국면 — `/ui-ux-design`

| 단계 | 무엇을 | 끝났다는 신호 |
| --- | --- | --- |
| **Step 2** 디자인 시스템 생성 | 색·폰트·spacing을 데이터에서 고름 | `dev/docs/design/<project>/MASTER.md` |
| **Step 2.5** 방향 심사 | "이게 이 브리프의 선택인가, 내 기본값인가" | `## Signature` · `## 방향 심사`가 채워짐 |
| **Step 2.6** 시안 캔버스 | `/design`으로 아트보드 발행 | 캔버스 URL |
| **👤 사용자 편집** | **캔버스에서 직접 고치고 Save** | 여정에서 **사람이 실행하는 유일한 단계** |
| **Step 2.7** 되쓰기 + 대조 | 고친 것을 `MASTER.md`로 | `design-sync.sh` exit 0 |
| **Step 4** 스택 가이드라인 | Next.js·shadcn 관행 적용 | (4종 외 스택이면 건너뜀) |

**Step 2.5가 중요한 이유** — AI가 만드는 디자인은 세 군집(크림+세리프+테라코타 / 근검정+산성
악센트 / 괘선 다단)으로 수렴합니다. 브리프가 그 방향을 **지정했다면 그대로 갑니다.** 지정하지
않았는데 거기 안착했다면 그건 선택이 아니라 기본값이므로 다시 고릅니다.

**Step 2.6~2.7이 하는 일** — 이게 없으면 사용자가 화면을 처음 보는 시점이 **코드 작성 이후**가
됩니다. 그때는 이미 컴포넌트를 만든 뒤라 방향을 바꾸는 비용이 가장 큽니다. 캔버스는 그
논쟁을 코드 이전으로 당깁니다.

> 📌 **캔버스가 없어도 됩니다.** `/design`이 없거나 거절하면 건너뜁니다 — **그때는 종전
> 방식 그대로**이고 잃는 것은 없습니다. 다만 레이아웃을 화면마다 한 줄씩은 적고 갑니다.

> 📌 **두 문서는 사본이 아니라 관할이 다릅니다.**
> `MASTER.md` = 토큰(색·폰트·간격)·시그니처 · 캔버스 = 화면 구성(배치·계층·카피·상태).
> 구현할 때 **둘 다 읽습니다.** 진입점은 `MASTER.md`의 `## 캔버스` 절이고, 그 절이 없으면
> 캔버스는 없는 것입니다.

#### 구현·검증 국면

| 단계 | 무엇을 | 자동으로 일어나는 것 |
| --- | --- | --- |
| **P4** 구현 | Claude가 코드 작성 | UI 파일을 만지면 `ui-design` 카드 자동 로드 · 시크릿 쓰면 훅이 차단 · 빌드 안 돌리고 끝내려 하면 Stop 훅이 막음 |
| **Step 6** 렌더 증명 | `/run`으로 띄우고 `ui-probe` | 스크린샷(모바일·데스크톱) · **콘솔 error 0** · 빈/로딩/에러 상태 렌더 |
| **P5** 마무리 | 클래스가 강도 결정 | 🟢 `/completion-review` · 🟡 `epcc-reviewer` |
| **P6** | 🔴만 | 다관점 팬아웃 + 사용자 확인 |
| 출하 | `/pr-prep` | 클래스가 요구하는 섹션(롤백 절차 등) 포함한 PR 본문 |

> ⚠️ **"빌드 통과"는 "화면이 나온다"가 아닙니다.** 타입체크는 빈 화면도, 콘솔이 터지는
> 화면도 통과시킵니다. 그래서 Step 6이 따로 있습니다. 브라우저가 없어 **판정을 못 하면
> Claude는 "확인함"이라고 적지 않고 "판정 불가"라고 적습니다.**

### 🅱 기존 기능 수정 · 버그 수정

**가장 짧은 경로입니다.** P4 → P5. 기획 문서를 만들지 않습니다.

```
요청 → (의도가 모호하면 질문) → 구현 → 빌드/테스트 → 마무리
```

- 테스트 러너가 있는 저장소에서 **동작을 바꾸면** `/test-driven-development`가 붙습니다
  (실패하는 테스트 먼저 → 최소 구현)
- 버그 재현이 먼저 필요하면 `/fix-issue`
- 건드린 경로가 🟡·🔴이면 그때만 리뷰가 붙습니다

> 💡 **이 경로에서 문서를 만들라고 하지 마세요.** 하네스는 "충족된 항목을 위한 문서를
> 만들지 않는다"를 규칙으로 갖고 있습니다. 세션을 넘어가는 큰 작업일 때만 `dev/active/`가
> 생깁니다.

### 🅲 이미 있는 저장소에 하네스를 나중에 설치했다

코드는 이미 자랐는데 규칙 카드는 비어 있는 상태입니다.

| 순서 | 명령 | 무엇을 |
| --- | --- | --- |
| 1 | `/epcc-init` | 기술 스택(프론트·백엔드·DB·인증)을 고르고 맞춤 가이드 생성 |
| 2 | `/codebase-survey` | **실제 코드를 실측**해 `project-structure`·`code-conventions` 카드를 갱신 |
| 3 | `doctor` | 설치가 실제로 됐는지 자기검증 |

**셋의 역할이 다릅니다** — 내장 `/init`은 `CLAUDE.md`를 처음 만들고, `/epcc-init`은 스택을
고르고, `/codebase-survey`는 **이미 있는 카드를 실물에 맞춰 갱신**합니다.

> ⚠️ 하네스는 **비침습**입니다. 원래 갖고 있던 `AGENTS.md`·`.github/`·`docs/`·기존
> `CLAUDE.md`는 명시적으로 요청하지 않으면 건드리지 않습니다.

### 🅳 스택을 바꾸거나 가이드를 다시 만든다

`/stack-guide-generator`를 부릅니다. 프리셋에 없는 조합(AWS·MongoDB·SvelteKit 등)도 됩니다.

가이드는 **조합이 아니라 축으로** 사전 제작돼 있습니다 — 프론트 4축 × 백엔드 8축. 조합
32개를 미리 만드는 대신 축을 조립합니다. 그래서 새 조합도 즉시 나옵니다.

### 🅴 낸 코드를 리뷰받았다 / 외부 AI 검증을 받았다

`/receiving-code-review`를 쓰세요. **피드백을 맹목적으로 수용하지 않습니다** — 실제 코드로
사실 확인한 뒤 채택하고, 틀린 지적은 근거와 함께 반박합니다.

| 리뷰 출처 | 어떻게 |

| `epcc-reviewer` 보고 | 〃 |

> 📌 **내장 도구와 겹치지 않습니다.** `/code-review`·`/simplify`·`/security-review`(브랜치
> diff)·`/init`·`/run`은 Claude Code가 제공합니다. 위 목록의 `/security-review`는 **전체 감사·
> 의존성·시크릿·결제** 담당으로, 내장이 다루지 않는 영역입니다.

---

## 6. 하네스가 나를 막을 때

훅 5종이 실시간으로 개입합니다. **막히면 대부분 이유가 있지만, 오탐도 있습니다.**

| 훅 | 언제 | 무엇을 |
| --- | --- | --- |
| `session-brief` | 세션 시작 | 운영 규칙·브랜치·미커밋 수·훅 생존 현황 주입 |
| `security-check` | 파일 쓰기·Bash 실행 **직전** | 시크릿 하드코딩·파괴적 명령 **차단(exit 2)** |
| `build-gate` | 대화를 끝내려 할 때 | 소스를 고쳤는데 빌드/테스트를 안 돌렸으면 **중단** |
| `handoff` | 압축·세션 종료 | 다음 세션용 인계 메모 저장 |
| `track-skill` | 스킬 호출 후 | 사용 기록 (계측용) |

### 막혔을 때 어떻게 하나

**① 진짜 위험한 경우 (대부분)** — 메시지가 이유를 말합니다. 시크릿은 환경변수로 빼고,
파괴적 SQL은 범위를 좁히세요.

**② 오탐인 경우** — 시크릿 **문자열이 들어 있지만 파일을 쓰지 않는** 조사 명령이 막히는
식입니다. 이럴 때:

- 명령을 파일로 써서 실행하거나, 세그먼트를 나눠 실행하세요
- 그리고 **Claude에게 오탐이라고 말해주세요** — `docs/lessons.md`에 기록되고,
  같은 장치에서 2건 이상 쌓이면 **규칙을 추가하는 게 아니라 조건을 좁히는** 후보가 됩니다

> ⚠️ **훅을 끄지 마세요.** 오탐 때문에 훅을 꺼버리면 그 훅의 차단력은 0이 됩니다.
> 하네스가 오탐을 집계하는 이유가 정확히 이것입니다.

**③ "판정 불가"라고 나온 경우** — 이건 차단이 아닙니다. 도구가 없거나(jq·playwright)
오프라인이라 판단할 수 없다는 뜻이고, 통과시킵니다. **다만 "확인함"으로 세지 않습니다.**

## 7. 세션이 길어졌을 때 — 컨텍스트 경계

국면(설계·구현·QA)이 **끝날 때** 정합니다. **국면 중간에는 자르지 않습니다.**
위에서부터 첫 「예」가 답입니다.

| # | 질문 | 예라면 |
| --- | --- | --- |
| ① | 다음 국면이 **이 대화를 1차 출처로** 쓰나? 창에 여유가 있나? | **계속한다** |
| ② | 지금 맥락이 다음 국면과 무관한가? | `/clear` |
| ③ | 다른 도구·디렉토리·사람에게 넘기나? | **핸드오프** |
| ④ | 감독 없이 끝낼 수 있나? | **서브에이전트** |
| ⑤ | 그 외 | `/compact` + 다음에 할 일을 함께 지시 |

**①을 가장 먼저 배제하는 이유** — 나머지 넷은 전부 1차 출처를 요약본으로 바꿉니다.
그리고 **그 손실은 되돌릴 수 없습니다.** 요약본에서 원본을 복구할 방법은 없습니다.

## 8. 자주 겪는 상황

**Q. Claude가 계속 질문만 합니다.**
「의도 명확」이 미충족이면 다른 게 다 채워져도 묻습니다. 무엇을·왜·어디쯤을 한 줄씩 주세요.

**Q. 간단한 수정인데 문서를 만들려고 합니다.**
작업 유형이 잘못 잡힌 것입니다. "기존 기능 수정이야, 바로 고쳐줘"라고 말하면 P4로 갑니다.

**Q. 리뷰가 안 붙습니다.**
경로가 🟢이면 정상입니다. 클래스는 규모가 아니라 경로가 정합니다. 꼭 받고 싶으면
"`epcc-reviewer`로 리뷰해줘"라고 직접 요청하세요.

**Q. 하네스가 제 프로젝트 규칙을 덮어씁니다.**
그러면 안 됩니다. 우선순위는 **사용자 요청 → 프로젝트 `CLAUDE.md` → 프로젝트 `.claude/rules/`
→ 저장소의 기존 코드 패턴 → 플러그인 가이드**입니다. **기존 코드 패턴이 플러그인
가이드를 이깁니다.** 반대로 동작하면 그것은 결함이니 알려주세요.

**Q. 설치는 됐는데 규칙이 안 보입니다.**
`.claude/rules/`에 카드가 실제로 있는지 확인하세요. 설치 성공과 자산 도달은 다릅니다.
`doctor`가 대조해줍니다.

**Q. 스킬이 안 불립니다.**
스킬은 description으로 발동합니다. 안 걸리면 `/스킬이름`으로 직접 부르세요.
