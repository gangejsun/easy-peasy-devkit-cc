# 작업 축 — 되돌림 가능성

규모(S/M/L)로 분류하지 않는다. 규모는 사람 판단을 요구해 드리프트하고,
**틀린 변수를 본다** — 5줄 마이그레이션이 400줄 리팩토링보다 위험하다.

## 클래스 판정 (경로 기반, 모델 판단 불필요)

**판정 경로의 정본은 세션마다 주입되는 T0 운영 규칙의 「되돌림 분류」 표다.**
여기에 옮겨 적지 않는다 — 사본은 드리프트 원천이다. 이 카드는 판정 *이후*를 담는다.

| 클래스 | 요구 — 누가 하는가 |
| --- | --- |
| **Irreversible** | `epcc-reviewer` 다관점 팬아웃(correctness·security·reversibility) + 사용자 확인 + 롤백 절차 |
| **Costly** | `epcc-reviewer` 필수 — **자기 리뷰로 대체하지 않는다**. 영향 범위(호출처) 제시 |
| **Reversible** | 바로 진행. 마무리 문서화는 `/completion-review` |

이 표의 `supabase/` 스키마·RLS · 운영 데이터 삭제/변환은 T0의 「auth/RLS · 운영 데이터」에
해당한다 — T0가 더 넓게 쓰였을 뿐 같은 것이다.

**둘 이상에 해당하면 높은 쪽을 따른다.** 애매하면 Costly로 본다.

**접근 정책 분기점** — 아래 패턴은 코드 변경으로 보여도 본질이 **UX/접근 정책 결정**이다.
auth 축(Irreversible)으로 판정하고, 선택지 간 실질 차이를 제시해 사용자가 고르게 한다:

- 라우트 가드 추가/이동/제거 (`redirect` → login, `(protected)` 그룹, layout 가드)
- 라우트 그룹 신설 (`(protected)` / `(public)` / `(auth)` 디렉토리)
- 인증 게이트 변경 (`middleware.*`의 가드 분기)
- 비인증/익명 사용자 노출 정책 변경

> 실사고 출처: 가드 이동이 "코드 리팩토링"으로 분류되어 접근 정책 변경이
> 사용자 확인 없이 통과한 사례. 기획/기술 추상화에 가려진 사각지대다.

## 진입 조건 4상태

Phase가 아니라 **상태**다. 순서가 없고, 미충족 항목만 채운다.

| 상태 | 확인 | 미충족 시 |
| --- | --- | --- |
| 의도 명확 | 무엇을·왜 만드는지 한 문장으로 말할 수 있는가 | 사용자에게 확인 |
| 컨텍스트 최신 | 근거로 삼는 문서/코드가 HEAD를 반영하는가 | `git log`로 확인 |
| 영향 반경 파악 | 어떤 파일·도메인·스키마가 바뀌는가 | grep으로 호출처 탐색 |
| 검증 경로 존재 | 됐는지 어떻게 아는가 (빌드/테스트/수동 확인) | 검증 방법 먼저 정의 |

> **넷 다 충족이면 준비 작업 0. 곧바로 구현한다.**
> 충족된 항목을 위한 문서를 만들지 않는다 — PRD·계획서를 이미 아는 것을 적기 위해 쓰지 않는다.

## 단계 (번호 없음, 각각 독립 호출 가능)

| 단계 | 언제 | 산출 |
| --- | --- | --- |
| `understand` | 영향 반경이 불명확할 때 | 탐색 결과 (파일 목록·호출 관계) |
| `plan` | 진입 조건 미충족 항목이 2개 이상일 때 | 계획 — 세션을 넘어갈 때만 파일로 |
| `build` | 항상 | 코드 |
| `verify` | Costly 이상 | 리뷰 결과 |
| `cross-check` | **Irreversible만** | 다관점 독립 검증 결과 |

번호를 붙이지 않는다. 번호는 의무를 만들고, 의무는 서류를 만든다.

## 워크스페이스

`dev/active/<slug>/`는 **작업이 세션을 넘어갈 때만** 만든다.
한 세션에 끝나는 작업에 워크스페이스를 만들지 않는다.
종결은 `dev/archive/<slug>/`로 **이동**해서 증명한다 — 상태 표기가 아니라 디렉토리 이동으로.

## 결정 기록 — `docs/decisions.md`

T0 「분기점」이 발동해 사용자가 고른 결과가 **Costly 이상**이면 그 선택을 기록한다.
`lessons.md`가 *실수*를 담는다면 여기는 *선택*을 담는다 — 둘은 다른 것이고, 섞으면
둘 다 못 쓰게 된다. **사소한 결정은 기록하지 않는다.**

```markdown
## [decision: <슬러그>] <한 줄 제목>

- 날짜: YYYY-MM-DD
- 상황: 무엇을 정해야 했는가
- 선택지: A / B (/ C) — **각각이 무엇을 포기하는지**
- 선택: <고른 것> — 사용자 결정 | 자동 판정
- 근거: 왜 그것인가
- 되돌림: <이 결정을 되돌리는 비용. 되돌릴 수 없으면 그렇게 적는다>
```

**선택지를 적지 않은 항목은 결정 기록이 아니라 감상문이다.** 나중에 이 파일을 읽는
쪽이 필요로 하는 것은 고른 것이 아니라 **버린 것과 그 이유**다.

읽는 쪽은 `epcc-planner`(계획 전 선행 결정 확인)와 `/pr-prep`(PR 본문 Decisions 줄)이다.
인용할 때는 「참조 신선도」 4축을 적용한다 — 결정 이후 정본이 바뀌었을 수 있고,
**재검증하지 않은 인용은 근거가 아니다.**

상한 30건. 넘으면 가장 오래된 것부터 `docs/decisions-archive.md`로 **이동**한다.
전제가 무효가 된 항목(스택 교체·요구 철회)은 나이와 무관하게 이동 대상이다.

## cross-check: 다관점 팬아웃

Irreversible 변경은 **서로 다른 렌즈로 독립 검증**한다. 같은 관점 N번이 아니라 다른 관점 N개.

- **correctness** — 로직이 명세대로인가, 엣지 케이스는
- **security** — 권한·RLS·입력 검증·시크릿 노출
- **reversibility** — 실패 시 롤백이 실제로 가능한가, 데이터 손실 지점은

각 렌즈는 독립적으로 판정하고, **과반이 문제 없음일 때만 통과**한다.
외부 모델 호출은 선택이다 — 렌즈 다양성이 본질이고 모델 다양성은 부수적이다.
