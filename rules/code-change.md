# 코드 변경 카드

`src/` 계열 파일을 편집할 때 로드된다. 일반적인 코딩 상식은 담지 않는다.
**모델이 반복해서 틀리는 것**만 남긴다.

## 변경 후 역추적

변경한 변수·함수를 grep해서 미사용 잔재를 정리한다. 개선을 하고 옛 코드를 남기는 것이
가장 흔한 실패다. 변수명이 바뀐 역할과 여전히 일치하는지 확인한다.

## 동일 패턴 전파

정규식·상수·시그니처를 바꿨으면 grep으로 **사용처를 전수 검색**해서 일괄 변경한다.
한 곳만 고치면 나머지가 조용히 어긋난다.

## 배선 확인 (존재 ≠ 실행)

규칙·상태값·핸들러를 도입할 때 CRUD 전 생명주기의 **실행 배선**을 확인한다.
"파일이 존재하는가"가 아니라 **"누가·언제 호출하는가"**까지 확인한다.

- 파일에 append하는 코드를 쓰면 로테이션/상한을 같이 넣는다
- 비정상 종료 시나리오를 고려한다
- 새 분기를 넣으면 그 분기로 실제 들어가는 입력이 있는지 확인한다

## 참조 신선도 (이전 작성물을 인용·확장하기 직전)

이전 코드·문서·SQL·보고서를 행동 근거로 쓰기 전에 4축을 점검한다:

1. 사용 중단된 이름·패턴의 잔재가 아닌가
2. 정본은 진화했는데 인용본(타입·미러·fragment)이 멈춰 있지 않은가 —
   base는 진화 체인의 **말단**이다 (DB 함수는 최초 정의가 아니라 가장 최근 `OR REPLACE` 본문)
3. 같은 정보가 여러 곳에 있을 때 정본(SSOT) 방향이 그대로인가 —
   미러는 통째 복사하지 않고 변경 섹션만 반영한다
4. 도구·라이브러리 **메이저 버전 업그레이드 후**에도 같은 패턴이 유효한가

이전 진단·리뷰 보고서는 **검토 영역의 힌트로만** 받는다. "Critical N건"이라 적혀 있으면
N건이 여전히 미해결인지 현재 정본을 grep으로 하나씩 재검증한 것만 채택한다.

위반 시그널: "이미 갱신된 항목의 회귀" 지적, "이전에 처리한 것 같은데" 류 사용자 반응
→ `docs/lessons.md`에 `[category: freshness]`로 기록한다.

## 검증까지가 한 동작

소스를 고쳤으면 **빌드/테스트 실행 → 결과 확인**까지 해야 변경이 끝난다.
`build-gate` 훅이 이를 강제하지만, 훅이 막기 전에 스스로 한다.

## 되돌림 클래스별 추가 요구

| 클래스 | 추가 |
| --- | --- |
| Irreversible (`migrations/`, auth/RLS, 결제·정산) | 적용 전 사용자 확인 필수. 롤백 절차를 함께 제시 |
| Costly (공유 패키지, public API, 타입 계약) | 영향 범위(호출처 목록)를 먼저 제시 |
| Reversible | 없음 — 바로 진행 |

## 의존성 추가 전 (설치 후 audit이 아니라 설치 전 점검)

새 패키지는 설치 전에 5가지를 점검한다: ①출처(공식 레지스트리·활성 저장소)
②이력(최근 업데이트·메인테이너 변경) ③의존성 트리(수상한 transitive 포함)
④커뮤니티 규모(다운로드·이슈 대응) ⑤패키지 매니저 audit — **Critical/High 발견 시
설치 중단 후 사용자 보고**. 10줄로 대체 가능한 기능이면 의존성을 추가하지 않는다.

## 자가 점검 (구현 완료 시)

- 요청하지 않은 파일을 고쳤는가
- "확장성을 위해" 추가한 코드가 있는가
- 제거해도 요청 기능이 동작하는 코드가 있는가

→ 하나라도 YES면 제거한다.
