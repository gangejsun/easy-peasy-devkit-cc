# 보안 카드

## 시크릿의 경계 — 값이 아니라 어느 쪽에 있는가

| 종류 | 둘 곳 |
| --- | --- |
| 서비스 롤·관리자 키 (`service_role`, admin SDK, 마스터 토큰) | **서버 전용.** 클라이언트 번들에 들어가는 파일에서 import 금지 |
| 결제 시크릿 키 | **서버 전용.** 서버 핸들러/액션에서만 |
| AI·외부 API 키 | **서버 전용.** 브라우저에서 직접 호출하지 않는다 |
| PEM 개인키 · 서비스 계정 JSON | 환경변수 경로 또는 파일시스템. 저장소에 넣지 않는다 |
| 공개 클라이언트 키 (anon key 등) | 클라이언트 가능 — **단 그것이 공개용으로 설계된 키일 때만** |

**공개 접두사를 붙이면 번들에 들어간다.** `NEXT_PUBLIC_` · `VITE_` · `PUBLIC_` · `EXPO_PUBLIC_`
류 접두사는 빌드 시 값이 정적으로 치환된다. 서버 전용 키에 이 접두사를 붙이는 것은
**노출이지 설정이 아니다.** 접두사를 붙이기 전에 "이 값이 브라우저에 보여도 되는가"를 묻는다.

## 입력 검증 경계

- 외부 입력(request body · query · 폼 · 웹훅 페이로드)은 **스키마 검증을 통과한 뒤에만**
  비즈니스 로직이나 DB 쿼리에 넘긴다. 검증 전 값을 그대로 흘리지 않는다
- 파일 업로드는 타입·크기 상한을 **서버에서** 강제한다. 클라이언트 검증은 UX이지 경계가 아니다
- 쿼리는 **파라미터화**한다. 값을 문자열로 이어 붙이지 않는다 (SQL·NoSQL 공통). 파라미터로
  넘길 수 없는 자리(테이블·컬럼·정렬 방향)는 **허용 목록**으로 좁힌다
- 신뢰 경계를 넘는 지점이 어디인지 모르면, 그 함수는 아직 검증 위치를 정하지 못한 것이다

## 인가 경계

- 서버 진입점(핸들러·액션·잡)에서 **인증 주체를 먼저 확인**한다. 클라이언트가 보낸
  사용자 식별자를 신뢰하지 않는다 — 세션·토큰에서 얻는다
- 보호 경로는 라우트 단위가 아니라 **데이터 접근 단위**로도 막는다. 화면 가드만 있으면
  API를 직접 호출해 우회된다
- 식별자를 받아 특정 레코드를 다룰 때 소유권은 **쿼리 조건에 넣는다.** 가져온 뒤 비교하면
  0행·경합·열거에 새고, 조건이 지워져도 테스트가 통과한다
- 행 수준 보안을 쓰는 스택이면 정책이 유일한 경계가 아니다 — 정책 + 애플리케이션 검사 둘 다.
  (테이블 생성 시 정책 동반 체크리스트는 `.claude/rules/data-modeling.md` §8)

## 출력 보안

- 원시 HTML 주입(`dangerouslySetInnerHTML` · `v-html` · `innerHTML =`)을 쓰지 않는다.
  불가피하면 sanitize 라이브러리를 통과시키고, **왜 불가피한지 주석으로 남긴다**
- 에러 응답에 스택 트레이스·DB 스키마·내부 경로를 싣지 않는다. 로그에는 남기고
  응답에는 사용자 친화적 메시지만 반환한다
- 리다이렉트 대상을 사용자 입력에서 받으면 **허용 목록으로 좁힌다** (오픈 리다이렉트)
- 인가 실패에서 **존재를 누설하지 않는다** — 남의 리소스는 403이 아니라 404다.
  둘을 구분하면 접근할 수 없는 것의 존재가 알려진다
