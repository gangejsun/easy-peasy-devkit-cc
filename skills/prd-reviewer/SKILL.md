# PRD Reviewer

기존 PRD 문서의 품질을 진단하고, 반영 위치를 명시한 개선안을 도출하는 스킬입니다. 단일 PRD와 모듈형 PRD(prd-overload + Phase Sub PRD + Shared 문서) 모두 지원합니다.

## 워크플로우

### Step 1: 대상 PRD 결정 + PRD 유형 감지 + 진단 범위 선택

#### 1-1: 대상 PRD 결정

| 상황                   | 동작                                           |
| ---------------------- | ---------------------------------------------- |
| 사용자가 PRD 파일 지정 | 해당 파일로 진행                               |
| PRD 파일 미지정        | `dev/docs/prd/` 탐색 후 목록 제시, 사용자 선택 |

#### 1-2: PRD 유형 자동 감지

| 감지 조건                                               | PRD 유형   | 진단 방식         |
| ------------------------------------------------------- | ---------- | ----------------- |
| `prd-overload.md` 존재 + `phases/`, `shared/` 폴더 존재 | **모듈형** | 6축 진단 (A~F)    |
| 단일 `.md` 파일                                         | **단일**   | 5축 진단 (A~D, F) |

#### 1-3: 진단 범위 선택

| 진단 범위    | 설명                                                        | 실행 Step                           |
| ------------ | ----------------------------------------------------------- | ----------------------------------- |
| 종합 진단    | 전체 축 검증 (단일: A~D+F, 모듈형: A~F)                     | Step 2 A→B→C(→E)→F → Step 3→4       |
| 특정 섹션    | 사용자 지정 섹션만 집중 진단                                | Step 2 A→B→C (범위 한정) → Step 3→4 |
| 구현 대조    | 코드베이스 대비 괴리 중심                                   | Step 2 D → Step 3→4                 |
| 모듈형 구조  | prd-overload 기준 크로스 문서 정합성 (모듈형 전용)          | Step 2 E → Step 3→4                 |
| 수정 후 검증 | PRD 수정 직후 일관성 + 설계 원칙 검증. 문서 의존성 카드가 트리거 | Step 2 C→E(모듈형)→F → Step 3→4     |

### Step 2: PRD 품질 진단

대상 PRD를 읽고 진단합니다. 각 축에서 발견한 이슈에 **반드시 PRD 내 위치(섹션명 + 해당 내용)**를 기록합니다.

**보고 기준 — 반증 가능성**: 이슈로 올리려면 *그 문장 때문에 구현이 갈리는 지점*을 쓸 수
있어야 한다. "~일 수 있습니다"는 이슈가 아니라 추측이다. 쓸 수 없으면 보고하지 않는다.

#### A. 구조적 완결성

템플릿(`skills/prd-generator/assets/prd-template.md`)의 필수 섹션이 실재하는가.
제목만 있고 본문이 빈 섹션은 **없는 것으로 센다** — 있는 척하는 섹션이 더 나쁘다.

```bash
grep -nE '^#{1,3} ' <PRD>            # 섹션 목록
grep -cE '^\| *FR-[0-9]' <PRD>       # FR 행 수 (0이면 A Critical)
```

- [ ] 문제 정의 · 목표/비목표 · 기능 요구사항 · 제약 · 열린 질문이 있는가
- [ ] **비목표**가 비어 있지 않은가 (범위를 닫지 않은 PRD는 구현에서 무한히 번진다)

#### B. 요구사항 명확성

FR 하나하나가 **수용 기준으로 검증 가능한가.** 판정 기준은 "이 문장만 보고 통과/실패를
가를 수 있는가" 하나다.

- [ ] 각 FR에 수용 기준이 있는가 · 우선순위(MoSCoW)가 있는가
- [ ] 실패·예외 경로가 적혀 있는가 (성공 경로만 있는 FR은 Important)
- [ ] 수치가 필요한 곳에 수치가 있는가 ("빠르게" → "p95 500ms 이내")

모호 표현은 **구현에 실질 영향이 있을 때만** 올린다 (Pitfalls 3번).

#### C. 내부 일관성

같은 사실이 두 곳에서 다르게 적혀 있는가. **PRD 결함의 대부분이 여기서 나온다.**

```bash
grep -noE '[0-9][0-9,.]*(원|%|초|ms|명|건)' <PRD> | sort -t: -k2 | uniq -f1 -D  # 같은 수치의 상충
grep -nE 'FR-[0-9]+' <PRD> | sort -u                                          # FR 참조 ↔ 정의 대조
```

- [ ] 수치가 섹션마다 같은가 · 상태 전이에 모순이 없는가
- [ ] 용어가 하나로 통일됐는가 — grep 한 번으로 끝내지 말고 **약어·동의어·복합명사 변형**까지
- [ ] 문서 내 링크·섹션 참조가 실재하는가

#### D. 구현 정합성 (구현 대조 모드)

PRD가 말하는 것과 코드가 하는 것의 괴리. **코드를 읽고 확인한 것만 적는다** —
"구현되지 않은 것 같다"는 이슈가 아니다.

- [ ] FR마다 구현 위치(파일·함수)를 찾았는가 / 못 찾았으면 미구현으로 표시했는가
- [ ] 코드가 PRD보다 앞서간 부분(문서에 없는 동작)이 있는가
- [ ] 괴리를 발견하면 **어느 쪽이 맞는지 정하지 않는다** — 사용자에게 선택지로 낸다

#### E. 모듈형 구조 정합성 (모듈형 PRD일 때만)

- [ ] `prd-overload.md`의 Phase 목록과 `phases/` 실물이 일치하는가
- [ ] Phase 간 의존 선언이 순환하지 않는가
- [ ] `shared/`의 항목이 **한 곳이 원본**인가 (여러 Phase가 같은 정의를 중복 서술하면 Critical)

```bash
ls phases/ ; grep -nE '^\| *Phase' prd-overload.md   # 선언 ↔ 실물
```

#### F. 설계 원칙 정합성 (단일·모듈형 공통)

프로젝트 `CLAUDE.md`·`.claude/rules/`가 선언한 원칙과 PRD가 충돌하는가.
**원칙의 문자적 해석에 머물지 말고 구현에 미치는 구조적 영향까지 본다.**

- [ ] 되돌림 클래스가 Irreversible인 요구사항(마이그레이션·auth·결제)에 롤백 서술이 있는가
- [ ] 프로젝트가 이미 쓰는 패턴과 다른 방식을 PRD가 요구하는가 (요구한다면 그 근거가 적혀 있는가)

### Step 3: 진단 보고서 생성

**심각도 기준:**

| 심각도    | 기준                              | 예시                                                     |
| --------- | --------------------------------- | -------------------------------------------------------- |
| Critical  | 구현 방향에 직접 영향, 모순/오류  | 수치 불일치, 상태 전이 모순, 용어 혼용, 끊어진 문서 링크 |
| Important | 명확성 부족으로 구현 시 혼란 가능 | 모호한 요구사항, 예외 케이스 누락, FR↔Screen 매핑 누락   |
| Minor     | 품질 개선, 가독성 향상            | 섹션 순서, 형식 통일, 사소한 오탈자                      |

### Step 4: PRD 업데이트 적용

사용자가 승인한 개선안만 PRD에 반영합니다.

### Step 5: 완료 보고

```
PRD 진단 및 업데이트가 완료되었습니다.

PRD 유형: [단일 / 모듈형]
진단 결과: Critical [N]건 / Important [N]건 / Minor [N]건
적용 항목: [N]건 / 전체 [M]건
문서 버전: [이전] → [현재]
역검증: [통과/잔존 N건]

파일: [PRD 파일 경로 또는 모듈형 구조 목록]
```

## Pitfalls

- 축 F 검증 시 원칙의 문자적 해석에 머물지 말 것 — 구현에 미치는 구조적 영향까지 추적
- 용어 일관성 검증 시 grep 한 번으로 끝내지 말 것 — 약어·동의어·복합명사 변형까지 검색
- "적절한", "필요 시" 같은 모호한 표현 자체를 Critical로 올리지 말 것 — 구현에 실질적 영향이 있는지가 기준
