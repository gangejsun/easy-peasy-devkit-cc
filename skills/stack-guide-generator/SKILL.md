# Stack Guide Generator

확정된 스택 조합으로 프로젝트 소유의 가이드 스킬을 생성한다.
구조는 `assets/guide-skeleton.md` 생성 규격서를 따르고, 내용은 조합 지식으로 채운다.

> **원칙: 본문을 먼저 만들고 검증한 뒤에만 설치한다.** description이 본문이 못 지키는
> 약속을 하는 스킬(placeholder)을 만드는 것이 이 스킬이 대체하는 실패 모드다.

## 프로세스 원칙 (2026-08-21 A/B 실측에서 도출)

생성 방식만으로는 품질이 나오지 않는다. **생성 + 검증 루프가 한 세트**다. 근거는
`dev/docs/skill-review/`의 A/B v1~v3 — 매 라운드에서 "자기보고 통과" 산출물에서
실결함이 추가로 나왔다.

| # | 원칙 | 실측 근거 |
| --- | --- | --- |
| 1 | **각색 금지, 규격서 기반 신선 생성** | 각색안은 설치 게이트 4항 불합격. 실패 원인은 내용 누출이 아니라 **맥락 관성**(원본에는 맞고 생성물에는 틀린 특성을 상속) |
| 2 | **허브만이 아니라 리소스 층위까지 슬롯 계약** | 슬롯 표 이전 산출물은 존재하지 않는 리소스 5~6개를 참조하는 깨진 허브였다 |
| 3 | **분량은 품질이 아니다** | 3,000줄 원본 vs 1,800줄 생성본에서 후자 우세. 감사 없는 축적은 부패도 함께 쌓는다 |
| 4 | **기계로 잡을 수 있는 건 전부 기계로** | 검출된 결함의 다수가 안목이 아니라 grep으로 잡혔다 (dangling·누출·예산·절단면·시그니처) |
| 5 | **생성자 ≠ 검증자** | 생성 에이전트는 매번 전항 통과를 자기보고했으나 독립 감사가 결함을 찾았다 |
| 6 | **감사 보고도 재확인 대상** | 감사자의 지적 일부가 오판이었다(규격 준수를 위반으로 판정) |
| 7 | **예산 상한에 붙이지 않는다** | 300줄에 도달한 파일은 다음 변경 때 저자가 아니라 예산이 삭제 대상을 고른다 |

## Step 1: 차원 확정

우선순위: `epcc.config.json`의 `techStack` → 부족한 차원만 인터뷰.

epcc-init을 거쳤으면 `techStack.presets`(2축 선택)과 `techStack.frontend`/`backend`가 이미
채워져 있다. **두 축을 모두 읽어 조합으로 다룬다** — 한 축만 보고 생성하면 서로를
고려하지 못한 가이드가 나온다 (아래 조합 의존성 참조).

| 차원 | 선택지 예 | 의존 규칙 |
| --- | --- | --- |
| 프론트엔드 | Next.js · React+Vite · SvelteKit · 없음(API 전용) | — |
| 백엔드 유형 | BaaS(Supabase·Firebase) · 클라우드 자체 구축 · 프레임워크 내장 | `techStack.presets.backend`가 있으면 **이미 확정** — 다시 묻지 않는다. 이 스킬을 단독 호출해 프리셋이 없으면 필수 질문 |
| 클라우드/호스팅 | AWS · GCP · Azure · Vercel · 자체 | 자체 구축 선택 시 필수 |
| DB | PostgreSQL · MySQL · MongoDB · DynamoDB | BaaS면 자동 추론 후 확인만, 자체 구축이면 필수 질문 |
| 데이터 액세스 | Prisma · Drizzle · SQLAlchemy · SDK 직접 | DB 확정 후 |
| 인증 | Supabase Auth · NextAuth · Cognito · 자체 | 백엔드 유형 연동 |

확정된 조합을 `epcc.config.json`의 `techStack.backend`에 기록한다 (스키마의 backendType·cloudProvider·database·dataAccess·auth 필드).

## Step 2: 생성 범위와 분기 — 축 팩을 먼저 조회한다

**사전 제작 단위는 조합이 아니라 축이다.** 조합은 40가지지만 축은 13가지(프론트 5 ·
백엔드 8)이고, 가이드 내용의 대부분은 한 축만의 함수다. 그러니 **없는 것만 만든다.**

```bash
ls "${CLAUDE_PLUGIN_ROOT}/guides/frontend/" "${CLAUDE_PLUGIN_ROOT}/guides/backend/"
ls "${CLAUDE_PLUGIN_ROOT}/guides/seams/"
```

**팩을 쓰기 전에 `pack.json`의 `fixesVariants`를 프로젝트의 확정 차원과 대조한다.**
축 팩은 프레임워크·ORM 같은 변형을 못박는다(`aws-container`는 Hono + Drizzle,
`node-api`는 Express + Prisma). 확정 조합이 그와 다르면 **없는 것이 아니라 틀린 것을
받는다** — 조립하지 말고 생성 경로로 보내거나 사용자에게 변형 변경 여부를 묻는다.
`fixesVariants`가 `{}`면 못박은 변형이 없다는 선언이므로 그대로 조립한다.

| 상태 | 동작 | 생성량 |
| --- | --- | --- |
| 두 축 팩 + 사전 제작 이음매 | **생성하지 않음** — `install-guide.sh` 조립만 | 0줄 |
| 두 축 팩 · 이음매 없음 | 팩 조립 후 **이음매만 생성** (축당 3파일) | ~1,100줄/축 |
| 한 축만 팩 | 그 축은 조립 + 이음매 생성, 반대 축은 **허브+전 리소스 생성** | 혼합 |
| 팩 없음 | 양쪽 전체 생성 (기존 경로) | ~2,300줄/축 |
| 프론트엔드 `none` (API 전용) | backend 쪽만 |
| 백엔드 `none` (정적/SPA+외부 API) | frontend 쪽만 (API 클라이언트 패턴 포함) |
| 두 축 모두 `none` | 아무것도 하지 않음 |
| 기존 생성본 존재 | Step 7의 스탬프 대조 — 수동 편집 감지 시 덮어쓰지 않고 diff 제시 |

### 팩이 있는 축에서 반드시 읽을 세 파일

팩과 이음매를 갈라 배송하면 **팩이 쓰는데 이음매가 안 주는 심볼**과 **팩이 선언한 정책을
이음매가 어기는 것**이 새 결함 부류가 된다. 게이트가 둘 다 검사하므로 생성 전에 읽는다.

| 파일 | 생성 에이전트에 전달할 것 |
| --- | --- |
| `guides/<축>/<팩>/ledger.md` | `requires` 표 전문 — **이음매가 반드시 export해야 하는 심볼 목록**이다. 종류가 `프로젝트`면 export, `라이브러리`면 import 바인딩, `교차축`·`생성물`이면 만들지 않는다 |
| `guides/<축>/<팩>/policies.md` | 기계 검사 표 + "사람이 지킬 것" 전문 — 이음매가 어기면 게이트 FAIL이다 |
| `guides/<축>/<팩>/pack.json` | `exampleDomain`(도메인 어휘 고정) · `seamSlots`(만들 파일 이름) · `resources`(Navigation Guide에 실을 팩 리소스 행) |

**허브(`SKILL.md`)도 이음매가 쓴다.** 팩의 `PACK.md`에서 `<!-- pack-slot: ... -->` 블록을
**그대로 옮기고**, 파일 끝의 "이음매가 채울 것" 표에 있는 슬롯만 새로 쓴다. 팩 조각을
고쳐 쓰면 다른 조합과 갈라져 팩의 의미가 사라진다.

### 조합 의존성 — 두 가이드는 서로의 함수다

**축이 하나 바뀌면 다른 축의 가이드도 달라진다.** 실측 근거: 같은 Supabase 백엔드인데
Next.js와 짝지으면 Route Handlers·Server Actions·미들웨어 세션 갱신 중심이 되고,
React+Vite SPA와 짝지으면 Edge Functions·브라우저 직접 호출·RLS 단독 방어 중심으로
**완전히 다른 backend-guide**가 나왔다.

생성 서브에이전트에 반드시 함께 전달할 두 가지:

| 항목 | 출처 | 두 가이드에 미치는 영향 |
| --- | --- | --- |
| **서버 코드가 어디 사는가** | 프론트엔드 프리셋의 `notes.serverCode` | backend-guide의 "표준 핸들러 형태" 슬롯 전체. 프론트에 서버 런타임이 있으면 거기에, 없으면 BaaS 함수·서버리스 함수·자체 서버에 |
| **보안 경계가 어디인가** | 백엔드 프리셋의 `notes.securityBoundary` | 양쪽의 인증/권한 슬롯. 서버 런타임이 있으면 애플리케이션 층 검사 + 데이터 층 정책 이중 방어, SPA면 데이터 층 정책이 사실상 유일한 경계 |
| **데이터 계층에 정책 엔진이 있는가** | 백엔드 프리셋의 `notes.securityBoundary`·`dataModeling` | **가장 크게 갈리는 변수.** 있으면(RLS·Security Rules) 이중 방어를 전제로 쓰고, 없으면(DynamoDB 등) 애플리케이션 층 소유권 검사 누락이 곧 데이터 유출임을 전제로 써야 한다. 여기를 틀리면 가이드가 안전하다고 착각하게 만든다 |
| **언어가 TS인가 JS인가** | `techStack.frontend.language`·프리셋의 `notes.language` | 타입 표준 슬롯의 존폐. JS면 그 슬롯을 JSDoc 규약·런타임 스키마 검증으로 대체하고, 생성 타입 절은 넣지 않는다 |

**정책 엔진 유무는 문구 한 줄이 아니라 가이드 전체의 전제다.** BaaS 조합에서 쓰던
"RLS가 백업이니 애플리케이션 검사는 이중 방어" 서술을 정책 엔진 없는 조합에 그대로
옮기면 정확히 반대 지침이 된다 — Step 5 감사의 보안 축이 이 오염을 잡는 대상이다.

frontend-guide의 **데이터 페칭·라우팅/인증·완전 예제** 슬롯은 백엔드 선택에 종속된다.
backend-guide의 **API 엔드포인트·완전 예제** 슬롯은 프론트엔드 선택에 종속된다.
나머지 슬롯(스타일링·상태 관리·컴포넌트 패턴 / 데이터 액세스·검증·테스트)은 축 내부에서
닫힌다 — 조합이 바뀌어도 대체로 유지된다.

## Step 2-A: 축 팩 저작 (유지자 경로 — 소비자 프로젝트에서는 돌지 않는다)

없는 축 팩을 새로 만드는 경로다. **이 절이 없어서 vue 팩 저작이 임기응변이 됐고 단일
에이전트 직렬로 64분 3초가 걸렸다** (실측 2026-08-23. Step 3-1이 설계한 병렬은 한 번도
쓰이지 않았다).

> **불변식: 병렬은 저작 방식만 바꾸고 통과 기준은 한 항목도 바꾸지 않는다.**
> 팩은 `--pack` FAIL 0 · `pack-smoke.sh` 통과 · 감사 3종을 거쳐야만 출하된다.
> 그러므로 병렬이 실패할 때 나타나는 증상은 "나쁜 팩이 출하된다"가 아니라
> **"관문에서 되돌려져 왕복이 는다"**여야 한다. 그것이 성립하도록 게이트가 병렬 고유
> 결함 두 부류(어휘 분기 · 중복 서술)를 직접 잡는다 — 아래 L0의 어휘 정책과 게이트의
> `check_duplicate_fences`다.

### L0 — 계약 동결 (메인 세션, 직렬, 1회)

메인 세션이 직접 쓴다. **내용이 아니라 계약**이므로 원칙 5(생성자≠검증자)에 저촉되지 않는다.

| 산출 | 내용 | 왜 여기서 동결하는가 |
| --- | --- | --- |
| `pack.json` | `exampleDomain` · `pkgs`(메이저 포함) · `resources[]`(파일명 + nav) · `seamSlots` · **`fixesVariants`** · `dataLayerPolicyEngine` | 파일 분할과 도메인 어휘가 갈리면 L1이 시작할 수 없다 |
| `ledger.md` **선언본** | `provides`(심볼 → **정의 파일 배정 + 형태**) · `requires`(종류·형태·이유) | 소유만 배정하고 **형태를 비우면 형제 클러스터가 시그니처를 추측한다** |
| `PACK.md`의 `directory-structure` 슬롯 | 디렉토리 트리 | 전 리소스가 경로를 참조한다 |
| `policies.md` **초안** | 축이 정하는 정책(보안·프레임워크 관용구) + **어휘 정책** | L1이 자기가 어길 규칙을 미리 알아야 한다 |

**인증 방식은 팩이 확정하지 않는다.** 세션 쿠키냐 베어러 토큰이냐는 프론트 축에 서버
런타임이 있는지의 함수 — **축이 아니라 조합의 함수**다. `requireAuth`·`useAuth`를
`requires`에 넣고 `auth-boundaries`를 `seamSlots`에 둔다 (aws-container·vue의 선례).
L0가 고정하는 것은 "어떤 방식"이 아니라 **팩이 가정하는 형태**(requires의 형태 열)다.

**`provides`에도 「형태」 열을 채운다 — 소유 배정만으로는 부족하다.** 실측(2026-08-23)에서
`getTask(ownerId, id)`를 형제 클러스터가 `getTask(id, ownerId)`로 불렀고, 두 인자가 모두
`string`이라 **TypeScript도 게이트도 잡지 못해** 모든 단건 조회가 404가 됐다. 원장은
"누가 정의하는가"만이 아니라 **"어떤 형태인가"**를 동결해야 한다 — `requires` 표에는
이 열이 처음부터 있었고 `provides`에만 없었다. 형태를 못박을 때 함께 적을 것:
인자 **순서**(같은 타입이 둘 이상이면 필수) · 반환 · 실패 시 무엇을 던지는가 ·
**호출자가 배선해야 하는 것**(예: `shutdown(server)`는 배수를 수행하므로 시그널 핸들러
**안에서** 불러야 한다 — 이 한 줄이 없어 부팅 즉시 종료하는 예제가 나왔다).

**어휘 정책을 L0가 발행한다.** `exampleDomain`에서 동의어 함정을 도출해 `policies.md`에
`forbid` 행으로 넣는다 — 클러스터를 갈라 쓰면 어휘가 갈리고(실측: `task` 217회 ↔
`note` 166회), 그것은 게이트가 잡아야 한다:

```
| `vocab-task` | forbid | guide | `\bnote(s)?\b\|노트` | — | `const notes = []` | 어휘는 Task/작업 (L0 발행) |
```

L0 산출은 **스크래치 파일 1개**로 묶어 요약하지 않고 **전문을** 모든 L1/L2에 붙여넣는다.

### 클러스터 나누기 — 팬아웃 단위는 파일이 아니다

**결합된 파일을 갈라놓는 것이 병렬의 주된 대가다.** 직렬 저작은 뒤 파일이 앞 파일을 읽어
어휘·어조·예제 변수명을 공짜로 맞추는데, 병렬은 그것을 잃는다.

**클러스터는 L0의 원장이 드러낸다** — 한 심볼의 정의 파일과 소비 파일이 다르면 결합이다.
vue 팩 기준 6파일 → 3클러스터 (`styling`+`component-patterns` / `loading-error-states`+
`types-and-testing` / `routing`+`state-management`). 클러스터가 1파일이면 파일 단위다.

### 파일럿 웨이브 — L0를 실검증한 뒤에 팬아웃한다

병렬은 저자의 자기수정 경로를 없앤다. 직렬 저자는 3번째 파일에서 "이 배정이 틀렸다"를
깨닫지만 병렬은 **틀린 L0로 전 클러스터를 동시에 버린다.**

1. 계약이 가장 무거운 클러스터 **1개만** 먼저 돌린다
2. `guide-gate.sh --pack`을 돌려 L0 배정이 실제로 성립했는지 본다
3. L0 수정이 필요하면 **여기서** 한다 (버리는 것은 클러스터 1개분)
4. 확정된 L0로 나머지 클러스터를 팬아웃한다

### L1 — 리소스 저작 (클러스터 단위 병렬)

전달: **L0 전문** · `assets/pack-resource-template.md` · 확정 스택 명세(버전 포함) ·
축 전제(서버 코드 위치 · 보안 경계 · **데이터 계층 정책 엔진 유무** · 언어) ·
자기 클러스터의 슬롯 계약 · 산출 경로.

**전달하지 않을 것**: 다른 팩의 경로, 인터뷰 맥락, 형제 클러스터의 초안.

L1 에이전트에게 그대로 지시한다:

> - 형식은 `assets/pack-resource-template.md`만 따른다. **다른 팩·가이드를 열지 않는다.**
> - **게이트가 검사하는 것을 손으로 재확인하지 않는다** — dangling 참조 · 줄 수 예산 ·
>   중복 export · env 커버리지 · 원장 대조 · 금지 키워드 · 정책 정규식. 너는 팩 전체를
>   볼 수 없어 **의미 있게 돌릴 수도 없다.** 팬인 후 메인 세션이 3초에 돌린다.
>   실측에서 생성자의 자기검증 52회가 잡은 실결함은 **0건**이었다
> - 네 시간은 **내용의 정확성**과 **네가 쓴 코드가 실제로 동작하는지**에만 쓴다
> - 파일 간 교차 참조는 **L0가 배정한 것만** 쓴다 (형제의 최종 내용을 모른다)
> - 보안 원시함수는 새로 쓰고 `assets/security-vectors.md`의 벡터를 실제로 통과시킨다.
>   결과(벡터·입력·출력·판정)를 반환 데이터에 싣는다
> - 버전 주장에는 `<!-- verified: 근거 -->` 또는 `<!-- unverified -->`를 단다

### L2 — 허브 조각 (L1과 병렬)

`PACK.md`의 나머지 `pack-slot` 블록. **L0의 선언 원장만으로 조립**하므로 L1을 기다리지
않는다. L1이 선언을 벗어나면 게이트의 원장 검사가 잡고 수리 대상은 허브 하나로 국한된다.

### L3 — 팬인 (메인 세션, 직렬)

0. **수리는 `SendMessage`로 같은 L1 에이전트를 이어 쓴다.** 새 `Agent` 호출은 컨텍스트를
   버려 파일을 처음부터 읽게 만든다 — 실측이 "벽시계를 지배한 것은 분량이 아니라 **검증
   왕복 횟수**"라고 판정했으므로 이 한 줄이 병렬 이득의 상당 부분을 지킨다
1. `bash <skill-dir>/scripts/guide-gate.sh --pack <팩경로>` → FAIL 0까지 수리
2. `bash <skill-dir>/scripts/pack-smoke.sh --pack <팩경로> --keep` → 실행 검증
3. `policies.md` 완성: L1 산출을 보고 내용 파생 정책을 추가하고 **각 행의 `증명 예`를 채운다**
4. 감사 3개 병렬 (Step 5)

**지적이 많으면 클러스터를 재위임하지 않고 정합 패스 1회로 수습한다** — 에이전트 1개가
팩 전문을 읽고 **어휘 통일 · 중복 서술 제거 · 교차 참조 수정만** 한다(내용 저작 없음).
그래서 병렬의 최악 비용은 `클러스터 병렬 + 정합 패스 1회`로 상한이 있다.

### 되돌림 — 인상이 아니라 측정값으로

아래 중 하나가 관찰되면 다음 팩의 기본값을 직렬(클러스터 1개)로 되돌리고 근거를 남긴다.
나머지 개선(템플릿 · smoke · 게이트 · 감사 3분할)은 병렬과 독립이므로 그대로 남는다.

| 기준 | 임계값 |
| --- | --- |
| 팬인의 병렬 고유 FAIL·REVIEW (어휘 · 중복 펜스 · 원장 배정) | 정합 패스 1회로 수습되지 않음 |
| 수리 왕복 (게이트 FAIL → 재위임 → 재게이트) | 3회 초과 |
| 감사 C의 교차 파일 지적 | vue 실측의 같은 부류 초과 |
| 생성 임계 경로 | vue 실측 64분을 줄이지 못함 |

### 하네스를 고쳤으면 출하 자산으로 회귀를 돌린다

**합성 픽스처는 미탐을 잡고, 실물은 오탐을 잡는다.** 이 게이트의 결함 4건이 전부
실사용에서만 드러났다 (node-api 실측): `check_env`가 헬퍼 선언을 미선언으로 오판 ·
`check_claims`가 태그된 주장을 인벤토리에서 제외 · 앞줄 태그 귀속 과대 · 보안 형태가
산문을 못 봄. 넷 다 합성 픽스처는 통과시켰다.

그래서 `--self-test`가 **출하 팩 전체를 회귀 코퍼스로** 돌린다. 새 검사를 넣었으면
자기검사 한 번으로 오탐이 드러난다 — **미탐만큼 오탐도 게이트를 못 쓰게 만든다.**

**측정 의무**: 단계별 벽시계(L0 / 파일럿 / 나머지 클러스터 / L2 / L3) · 서브에이전트
토큰 · 도구 호출 · 감사 지적 부류별 건수 · 위 되돌림 기준 4개의 실제 값을
`dev/docs/skill-review/`에 기록한다. **실측 없이 "빨라졌다"고 쓰지 않는다** —
직전 세션의 추정(20~40분)이 실측 64분으로 틀렸다.

## Step 3: 생성 — 격리 서브에이전트에 위임 (원칙 5)

### Step 3-0: 두 가이드를 만든다면 — 와이어 계약을 먼저 확정한다 (필수)

**격리 생성의 대가는 두 가이드가 서로 합의하지 못한다는 것이다.** 실측에서 프론트와
백엔드를 병렬 격리 생성했더니 응답 봉투·페이지네이션·인가 실패 상태 코드가 전부
어긋나, 완전 예제와 폼 에러 흐름이 통째로 실행 불가가 됐다. 격리는 **맥락 관성**을
막기 위한 것이지 계약까지 끊으라는 뜻이 아니다.

그래서 메인 세션이 `assets/wire-contract.template.md`(5항목 양식)를 채워 **스크래치 파일
1개**로 만들고, 요약하지 않고 **파일 전문을 양쪽에 그대로 붙여넣는다**. Step 4의 `--pair`가
같은 파일로 대조하므로 전달한 텍스트와 검사하는 텍스트가 같아야 한다. 한쪽만 생성하더라도
상대가 이미 존재하면 그 상대를 읽어 같은 양식을 채운다 (없을 때만 건너뛴다).

### Step 3-1: 생성 위임 — 3층, 결합 클러스터 단위 병렬

가이드당 에이전트 1개가 ~2,300줄을 **직렬로** 쓰면 실측 36.6분이다. 계약 규율은 그대로
두고 **층 2를 쓰는 주체만** 파일 단위로 넓힌다. 메인 세션이 직접 쓰지 않는 이유는
Step 4~5의 검증이 자기 채점이 되지 않게 하기 위함이다 (원칙 5).

| 층 | 하는 일 | 동시성 |
| --- | --- | --- |
| **L0 계약** (메인 세션) | Step 3-0의 계약 파일 + **팩의 `ledger.md` requires·`policies.md` 병합** + **심볼 원장 선언**(각 파일이 소유할 심볼을 미리 배정) | 1개 |
| **L1 리소스** | **결합 클러스터마다** 서브에이전트 1개. 입력 = 동결된 L0 + 스택 명세 + 구조 템플릿 | 클러스터 수만큼 병렬 |
| **L2 통합** | 완전 예제. **선언 원장만으로 조립**하므로 L1과 동시 실행 가능 | 축당 1개, L1과 병렬 |

**동시성이 안전한 이유.** 실측에서 병렬 격리 생성이 깨진 원인은 두 가이드가 와이어 계약에
합의하지 못한 것이었고 해법은 Step 3-0이다. 2개→N개로 넓혀도 그 위험은 커지지 않는다 —
**L0이 파일 간 사항을 전부 동결한 뒤에만 L1이 시작하기 때문이다.** 새로 생기는 위험은
형제 리소스 간 불일치이고, 게이트의 dangling·원장·env·정책 검사가 이미 파일 간 검사다.

**팬아웃 단위·파일럿 웨이브·정합 패스·되돌림 기준은 Step 2-A와 같다.** 그쪽이 정본이므로
여기에 옮겨 적지 않는다 — 병렬의 대가(직렬이 공짜로 주던 서술 일관성, L0 오류의 전면
파급, 수리 왕복)와 그 완화가 전부 거기에 있다.

> **L2를 L1과 병렬로 돌리는 것은 규율 변경이다.** 기존 규격은 "원장을 쓰면서 유지하고
> 완전 예제를 원장만으로 조립"인데, 이를 "L0에서 원장을 **선언**하고 L1·L2가 함께 준수"로
> 바꾼다. L1이 선언을 벗어나면 게이트의 원장 검사가 잡고, 그때 수리 대상은 완전 예제
> 하나로 국한된다. 어긋남이 잦으면 L2를 L1 뒤로 되돌린다 (임계 경로 +5분).

전달할 것: **두 축 전체의 확정 스택 명세**(버전 포함) · Step 2의 조합 의존성 항목
(서버 코드 위치 · 보안 경계 · 정책 엔진 유무 · 언어) · **Step 3-0의 계약 파일 전문**
(두 가이드면 양쪽에 토씨까지 동일하게) · **패키지 매니저**(프리셋의 `packageManager`) ·
**고정 패키지와 메이저 버전 목록**(생성 스탬프의 `pkgs=`가 된다 — 없으면 이후 드리프트
검사에 대조 대상 자체가 생기지 않는다) · 규격서와 게이트 스크립트의 절대 경로 · 산출 위치 ·
아래 생성 규칙 · "최종 텍스트는 데이터로 반환(파일 목록·줄 수·슬롯 매핑·공백 슬롯·**원장**)".

frontend-guide를 만드는 에이전트에게도 **백엔드 축을 알려준다**(그 반대도 마찬가지).
한 축만 알려주면 데이터 페칭·인증 슬롯을 채울 수 없거나 틀리게 채운다.

**전달하지 않을 것**: 인터뷰 대화 맥락, 다른 프리셋 이야기 (맥락 관성 차단).

생성 규칙 (서브에이전트에게 그대로 지시한다):

1. `assets/guide-skeleton.md`를 읽고 필수 섹션 8개 골격을 만든다
2. **의존 순서대로 쓰고, 쓰면서 심볼 원장을 유지한다 (계약 → 소비 → 통합).**
   실측 55건 중 약 70%는 지식 부족이 아니라 순서 문제였다(양쪽을 다 쓰고 대조하지 않음).
   순서를 바꾸면 그 부류가 구조적으로 불가능해진다:
   - **층 1 · 계약**: 와이어 계약 · env 스키마 · 도메인 스키마/타입을 **먼저** 쓴다.
     이후 모든 리소스가 참조하는 유일한 정본이다
   - **층 2 · 소비**: 리소스를 쓰면서 새로 도입한 **프로젝트 로컬 심볼을 원장에 등재**한다
     (라이브러리 API는 제외). 행 형식은 `| 심볼 | 정의 파일 | 소비처 |` —
     예: ``| `requireOwner` | auth-and-permissions.md | api-endpoints.md, complete-example.md |``
   - **층 3 · 통합**: 완전 예제를 **원장만으로 조립**한다. 원장에 없는 심볼을 쓰지 않고
     (미정의 호출 불가), 소비처가 빈 심볼은 여기서 소비하거나 삭제한다 (유령 정의 불가)

   원장은 반환 데이터의 일부다 — 게이트가 이 표로 실제 정의·소비를 기계 대조한다
3. 내용 슬롯을 확정 조합의 지식으로 채운다:
   - 검증 가능한 사실(공식 문서 수준의 표준 패턴)만 단정형으로 쓴다
   - 프로젝트에 실재하는 구조(디렉토리·설정)가 있으면 관례보다 우선한다
   - 확신이 없는 패턴은 쓰지 않는다 — 빈 슬롯이 틀린 내용보다 낫다
   - **형식은 `assets/pack-resource-template.md`를 따른다. 다른 팩·가이드를 열지 않는다.**
     이전 규격은 "형식만 참조, 내용 복사 금지"라는 방화벽을 지시로 걸었고
     **실측(2026-08-23)에서 실패했다** — 깨진 `safeReturnTo`가 react-vite 팩에서 vue 팩으로
     그대로 복사됐고 같은 결함이 출하본 네 곳 전부에 있었다. 지시로는 막히지 않는다
   - **보안 원시함수(경로 검증·토큰 비교·이스케이프·리다이렉트)는 반드시 새로 쓴다.**
     `assets/security-vectors.md`의 해당 벡터 **전부**를 네 구현에 실제로 통과시키고
     결과(벡터·입력·출력·판정)를 반환 데이터에 포함한다. 게이트의
     `check_security_shapes`가 알려진 취약 형태를 FAIL로 막지만 **막는 것은 이미 아는
     형태뿐**이다. 데이터 계층 정책 엔진 유무가 정반대인 조합의 방어 서술을 옮기면
     뜻이 뒤집힌다 — `pack.json`의 `dataLayerPolicyEngine`을 먼저 읽는다
   - **버전 주장에는 태그를 단다** — `vN에서 추가/제거` · `이제는` · `더 이상` 류를 쓰면
     같은 줄이나 앞 줄에 `<!-- verified: 근거 -->` 또는 `<!-- unverified -->`.
     게이트가 태그 없는 주장을 모아 감사 B에 넘긴다 (실측: 이 부류 5건이 거짓이었다)
4. resources/를 규격서의 **리소스 슬롯 표**에 따라 구성한다 — 필수 슬롯 7개를
   전용 파일 또는 병합으로 커버하고(확신 부족 슬롯은 비우되 보고에 명시),
   슬롯 수에서 도출한 6~10개 파일로 분할해 Navigation Guide에 전부 매핑한다
5. 산출 위치: 프로젝트의 `.claude/skills/frontend-guide/` · `.claude/skills/backend-guide/`
6. **반환 전에 스스로 게이트를 돌린다** — `guide-gate.sh --guide <경로> --generated`로
   **FAIL 0**을 만든 뒤 반환한다. WARN·REVIEW는 고치지 말고 **사유를 붙여 보고**한다
7. **관계형 DB면 데이터 모델링 카드와 연결한다 — 복사하지 않는다.** 정본은
   T1 규칙 카드(`.claude/rules/` 아래 `data-modeling.md`)로 epcc-init이 모든 프리셋에
   설치하며, `paths:`(supabase·migrations·db·prisma·drizzle) 매칭 시 자동 로드된다.
   생성하는 backend-guide에는 다음만 넣는다:
   - Navigation Guide에 1행: 테이블·마이그레이션 설계 → 데이터 모델링 카드 (자동 로드) 안내
   - **PostgreSQL이 아닌 RDB(MySQL 등)**: "카드의 PG 특화 절(§5·10·14·16·18)은 원칙만
     취하고 문법은 이 스택으로 치환" 1줄을 명시
   - **NoSQL(MongoDB·DynamoDB)**: 카드는 paths 미매칭으로 휴면 — 해당 DB의 모델링
     패턴(문서 설계·파티션 키 등)을 조합 지식으로 리소스에 직접 작성

   > 정본을 스킬 리소스로 복사·적응하지 않는 이유: 사본은 플러그인 갱신에서 끊긴
   > 드리프트 원천이다. 단일 카드 + 버전 스탬프 갱신이 v3의 배포 방식이다.

## Step 4: 기계 검증 게이트 — 메인 세션이 직접 실행한다

생성자도 반환 전에 같은 게이트를 돌리지만 **돌렸다는 보고 자체가 자기보고다** (원칙 5).

축 팩을 저작했다면 **조립 전에 `--pack`으로 먼저** 검사한다 (Step 2-A의 팬인 지점).
축 안에서 닫히는 검사만 돌리고 조합의 함수인 것(`requires` 충족 · `--pair` ·
대상=seam 정책)은 건너뛴 것을 명시 보고한다.

```bash
bash <skill-dir>/scripts/guide-gate.sh --pack <팩경로>
```

조립본에는 아래를 돌린다.

```bash
bash <skill-dir>/scripts/guide-gate.sh --guide <가이드경로> --generated \
  --pm <패키지매니저> --ledger <생성자가 반환한 원장> --forbid <확정 조합에 없는 스택 키워드> \
  --assembly <가이드경로>/assembly.json      # 팩을 조립한 축에서만 — 아래 참조
# 두 가이드를 만들었으면 계약 정합도 — 한쪽만 읽는 감사는 이 어긋남을 못 잡는다
bash <skill-dir>/scripts/guide-gate.sh --pair --contract <Step 3-0의 계약 파일> \
  --frontend <프론트 경로> --backend <백엔드 경로>
```

**`--assembly`를 빼먹으면 팩 경계 검사가 통째로 꺼진다.** `install-guide.sh`가 남긴
`assembly.json`을 주면 두 검사가 켜진다:

| 검사 | 잡는 것 |
| --- | --- |
| 팩 인터페이스 | 팩의 `requires`를 이음매가 정의하지 않음 → 팩 예제가 실행 불가 |
| 정책 원장 | 팩이 선언한 파일 간 불변식을 이음매가 어김 (**실측 감사 57건 중 26건이 이 부류**) |

**게이트가 소유하게 된 것 (v3.13.0)** — 프롬프트나 사람의 기억에 있던 것을 옮겼다:

| 검사 | 대체한 것 |
| --- | --- |
| 정책 표의 `증명 예` 열 단언 | "정책마다 결함 픽스처를 만들어 잡히는지 돌리기" — **vue 저작의 벽시계를 지배했다.** 이제 밀리초에 단언한다 |
| `check_security_shapes` | 오픈 리다이렉트의 두 재발 형태. 팩별 정책이 아니라 축 무관 형태이므로 게이트 본체가 소유한다 |
| `check_claims` | 감사자에게 넘길 "버전 주장 목록"을 손으로 모으던 일. WARN + 인벤토리로 전수 수집한다 |
| `check_duplicate_fences` | 병렬 저작이 만드는 중복 서술. 원장은 심볼만 보고 서술은 보지 않는다 (REVIEW) |
| `fixesVariants` ↔ `pkgs` 정합 | 팩이 못박은 변형을 선언하지 않아 조립 시점에 대조할 수 없던 것 |
| `provides` 「형태」 열 강제 + 인자 개수 대조 | **치명 결함 2건의 단일 원인.** 소유 파일만 배정하면 형제 클러스터가 시그니처를 추측한다 |
| `check_blocking_proof` | 「차단 장치」로 제시된 테스트가 부정 단언만 걸어 구현을 통째로 실패시켜도 통과하던 것 (REVIEW) |
| `--self-test`의 **출하 팩 회귀 코퍼스** | 합성 픽스처는 **오탐을 못 잡는다.** 이 게이트의 결함 4건이 전부 실사용에서만 드러났다 — 이제 새 검사가 실물에 오탐하면 자기검사가 즉시 빨개진다 |

정책 검사는 `codelines()` 출력에만 걸린다 — 산문·주석·안티패턴 예시를 세면 전부
위양성이다 (개발 중 8건 확인). 정규식이 위양성을 내면 고칠 것은 코드가 아니라
**팩의 `policies.md`**다: 예외 파일을 지정하거나 정규식을 좁힌다.

**FAIL이 하나라도 있으면 설치하지 않는다** — 실패 항목을 서브에이전트에 돌려보내 수리시키고
다시 실행한다. WARN은 Step 7 보고에 싣는다. REVIEW는 **항목마다 정당화하거나 수리한다**:
기계가 판정할 수 없는 자리이므로 침묵 통과가 곧 결함 통과다.

### Step 4-1: 실행 검증 — 읽어서 안 잡히는 부류가 있다

**실측(2026-08-23)에서 기계 게이트 전항을 통과한 뒤 남은 결함은 거의 전부 실행으로
잡혔다.** 감사자가 스크래치에 실제 프로젝트를 만들어 vue-tsc·node를 돌려 찾았다 —
오픈 리다이렉트 · `:key` 재마운트 · msw import 누락 · 테스트 하네스의 스프레드 ·
`defineConfig`의 `test` 키. 그 자발적 행위를 파이프라인의 단계로 올린다.

```bash
bash <skill-dir>/scripts/pack-smoke.sh --pack <팩경로> --keep
```

| 하는 일 | 비고 |
| --- | --- |
| `<!-- file: 경로 -->`로 **완전 파일을 주장한 펜스**만 실파일로 복원 | 발췌를 전부 컴파일시키려 하면 위양성 늪이 된다. 주장은 저자의 opt-in이다 |
| 원장 `requires`의 미해소 import를 스텁으로 채움 | 팩만 놓고 보면 이음매 심볼은 항상 미해소다 |
| 구문 검사 (`node`의 타입 스트리핑 — 오프라인) | JSX·SFC는 스트리핑 대상이 아니라 **미검사로 명시 보고**한다 |
| 타입체크 (`tsc`) | 없으면 **skip을 명시 보고**한다 — 미검사이지 통과가 아니다 |
| `assets/security-vectors.md`의 복귀 경로 벡터 12건 실행 | **실측 최대 발견이 이 부류였다.** 차단 10 · 정상 통과 2를 모두 확인한다 |

`--keep`으로 남긴 작업 디렉토리와 `vector-report.tsv`를 **감사 A에 그대로 넘긴다** —
감사자가 스크래치 프로젝트를 처음부터 만드는 비용의 상당 부분이 여기서 이미 끝나 있다.

툴체인 프로필은 `scripts/profiles/<이름>.sh`다. 현재 `node-ts` 하나이고 **`python`은
선언된 공백**이다 (fastapi 팩을 만들 때 채운다). 프로필이 없으면 스크립트가 skip을
명시 보고한다 — 침묵 생략은 금지다.

#### 스키마 실행 (검증 라이브러리를 고정한 가이드)

실측 최악의 결함은 `partial()`과 `default()`를 겹쳐 **부분 업데이트가 보내지 않은 필드를
기본값으로 덮어쓰는** 스키마였다 — 문법은 완벽했고 실행만이 드러냈다. 가이드가 검증
라이브러리를 고정했다면 스크래치에 그것만 설치해 스키마 코드펜스를 파싱시킨다:

| 입력 | 확인할 것 |
| --- | --- |
| 빈 객체 | 필수 필드가 실제로 거부되는가 |
| 필드 1개만 담은 부분 업데이트 | **나머지 필드가 조용히 채워지지 않는가** |
| 미지 키 포함 | 통과·제거·거부 중 무엇인가 — 가이드의 서술과 같은가 |

결과가 가이드의 서술과 다르면 고칠 것은 스키마가 아니라 **그 서술**이다.

## Step 5: 독립 적대적 감사 (원칙 5)

기계 게이트를 통과해도 설치 확정이 아니다. 기계가 못 잡는 것 — 부정확한 지침, 허브와
리소스의 규칙 충돌, 보안 판단의 허점 — 은 사람 눈에 해당하는 층위가 필요하다.

`assets/audit-prompt.md`의 템플릿을 채워 **감사 3개를 병렬로** 띄운다.
감사자에게 생성 대화 맥락을 주지 않는다 — 산출물만 읽어야 독립적이다.

**3분할하는 이유**: 실측에서 감사 1개가 1,946줄을 전수로 읽어 20분이었다. 실제로 결함을
잡은 세 경로가 서로 독립적이라 갈라도 손실이 없다 — 최대 발견(오픈 리다이렉트)은 A에,
거짓 버전 주장 5건은 B에 온전히 들어간다.

| 감사 | 입력 | 담당 |
| --- | --- | --- |
| **A. 실행** | `pack-smoke.sh --keep`의 작업 디렉토리 + `vector-report.tsv` + 팩 | 보안 · 절단면 중 **실행으로 확인 가능한 것**. 리포트에서 출발하므로 스크래치를 처음부터 만들지 않는다. `tsc`가 skip으로 남았으면 **그것을 채우는 것이 A의 첫 일**이다 |
| **B. 버전 주장** | 게이트 `check_claims` 인벤토리 | 정확성의 버전 주장 부분. 참/거짓/확인 불가를 한 줄씩 판정한다 |
| **C. 교차 파일** | 팩 전문 + `policies.md` + `ledger.md` | 자기모순 · 슬롯 계약 · 유령 심볼 · **정책이 선언한 것과 리소스가 실제로 하는 것의 불일치**(실측 26건 부류) · 어휘·서술 일관성 |

**세 감사 모두에게 게이트 출력 전문을 준다** (규격 적합을 다시 세지 않게 한다).
**전수 읽기는 C가 온전히 소유한다** — A·B는 좁은 입력만 받으므로 절단면 검사법
("전문을 읽으며 의심 이름을 모으고 grep으로 확정")을 수행할 수 있는 것은 C뿐이다.
C에게 A의 실행 리포트를 함께 준다.

**팩을 조립한 축은 감사 범위를 좁힌다.** 팩 파일은 플러그인이 사전 감사한 자산이므로
매 프로젝트에서 다시 감사하지 않는다. 감사자에게 `assembly.json`의 `packFiles`를 주고
이렇게 지시한다:

> 아래 파일은 **기준선 자산**이다: `<packFiles>`. 내용의 정오를 다시 판정하지 말고,
> **이음매 파일과 이 기준선의 상호작용만** 본다 — 이음매가 팩의 심볼을 잘못된 형태로
> 쓰는가, 팩이 선언한 정책과 어긋나는 서술을 하는가, 팩이 전제한 것(정책 엔진 유무·
> 서버 코드 위치)과 반대로 쓰는가. 나머지는 이음매 파일만 전수 감사한다.

이 좁히기가 감사 비용의 대부분을 줄인다 (읽을 분량이 절반 이하가 된다). 다만
**팩↔이음매 경계는 오히려 더 본다** — 갈라 배송하면서 새로 생긴 표면이기 때문이다.
**버전 주장 목록은 이제 게이트가 만든다** (`check_claims`의 인벤토리). 손으로 모으지
않는다 — 전수성이 사람의 성실함에 달려 있으면 놓친다. 그 목록이 감사 B의 입력 전부다.
잘못 확신한 지식은 생성 규율로 막을 수 없다 — 모델은 자기가 틀렸다는 것을 모른다.

## Step 6: 수리 — 감사 지적을 재확인한 뒤에 (원칙 6)

**감사자도 틀린다.** 실측에서 감사 보고의 일부가 오판이었다. 따라서:

1. 각 지적을 `파일:줄`로 **직접 열어 재확인**한다. 확인되지 않는 지적은 수리하지 않고
   그 사실을 보고에 남긴다
2. 확인된 결함만 수리한다 (치명·높음은 필수, 보통·낮음은 사용자 판단)
3. 수리 후 **Step 4를 다시 실행**한다 — 수리가 새 결함을 만드는 것이 흔한 실패 모드다
4. 치명 결함이 수리 불가면 설치하지 않고 사용자 판단을 받는다

## Step 7: 스탬프와 보고

- 각 SKILL.md에 생성 스탬프 기록 (skeleton의 형식 — 생성물에만 붙인다)
- 사용자 보고: 생성된 스킬 2개(또는 1개)·리소스 수·**게이트의 WARN 전량과 REVIEW 판정
  사유**·**감사 결과와 수리 내역**·**공백 슬롯 목록**(있으면)·"다음 세션부터 자동 트리거됨"
- 재생성 요청 시: 스탬프의 stack= 값과 새 조합을 비교해 변경 차원을 보고하고,
  수동 편집이 감지되면 편집 부분 diff를 보여준 뒤 사용자 확인을 받는다

## 생성 이후 — 부패는 시간이 만든다

오늘 정확한 가이드도 라이브러리 메이저 버전이 오르면 낡는다. 실측에서 실전 검증이
누적된 원본이 오히려 폐기 API·이전 버전 관용구·보안 결함을 안고 있었고, **명시적으로
감사를 돌리기 전까지 몇 달간 아무도 발견하지 못했다.**

- 스택 의존성의 메이저 버전이 오르면 해당 가이드에 Step 5 감사를 다시 돌린다.
  **사전 제작 가이드**는 SKILL.md 첫머리의 `epcc-guide-baseline` 줄이 그 판단 근거다 —
  감사·수리 후 `verified` 날짜와 버전 목록을 반드시 갱신한다 (갱신하지 않으면 다음
  점검이 낡음을 놓친다)
- 사용 중 발견한 결함은 `docs/lessons.md`에 기록한다 — 3건 이상 누적되면 doctor가
  승격 후보로 보고한다 (규칙 카드로 올릴지, 가이드를 고칠지 판단)
