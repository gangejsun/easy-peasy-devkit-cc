# 가이드 생성 규격서 (Guide Skeleton Spec)

생성되는 frontend-guide / backend-guide가 반드시 따라야 하는 구조.
nextjs-frontend/backend-guide의 실증된 골격에서 도출했으며, 2026-08-21 재기반(A/B v2)
이후에는 그 원본들 자신도 이 규격서를 따른다 — 규격서와 원본은 상호 정합 상태다.
사전 제작본은 현재 2쌍이다(`nextjs`×`supabase`, `react-vite`×`aws-container`).

> **동기화 의무**: 사전 제작 가이드(실증 원본) 어느 쌍이든 스택 무관 범주(보안·반복 UI·
> 테스트 등)가 추가되면 이 규격서의 해당 슬롯에도 반영한다. 두 쌍은 스택이 정반대이므로
> (데이터 계층 정책 엔진 유무) **양쪽에서 공통으로 성립하는 것만 보편 범주다** —
> 한쪽에서만 참인 서술을 슬롯 계약에 올리면 다른 조합의 생성물을 오염시킨다.
> **이 의무는 실측에서 한 번 깨졌다** (2026-08-23): 「인증/미들웨어 경계」 슬롯이
> "권한은 이중으로 건다"를 무조건으로 못박아, 정책 엔진이 없는 축의 생성물에
> 정확히 반대 지침을 요구했다. 조건부 서술로 고쳤다 — 슬롯 계약에 스택 전제를
> 심을 때는 **그 전제를 읽는 필드를 함께 지목한다**.
> **규격서가 생성물의 도달 상한이다** — 여기에 없는 항목은 생성 가이드에 보장되지 않는다.
> 본문 섹션만이 아니라 **리소스 층위도 동일하다**: 원본에 새 리소스 카테고리가 생기거나
> 기존 리소스에 스택 무관 심화 범주가 추가되면 아래 리소스 슬롯 표에도 반영한다.

## 구조와 내용의 구분

- **구조(스택 무관)**: 섹션 골격·순서·형식. 아래 표의 전 항목. 생성 시 변경 불가
- **내용(스택 고유)**: 각 슬롯을 채우는 실제 지식. 확정된 스택 조합에서만 도출한다.
  다른 스택의 내용(예: Supabase 패턴을 AWS 가이드에)을 누출하면 자기 검증 실패다

## 필수 섹션 (순서 고정)

| # | 섹션 (구조) | 내용 슬롯 | 예산 |
| --- | --- | --- | --- |
| 1 | frontmatter | `name:`은 디렉토리명과 일치 · description은 "무엇을 다루는가 + Use when creating or modifying <작업 목록>" 형식. **게이팅 접두사는 배포 형태를 따른다**: 프로젝트에 생성·설치되는 가이드는 그 프로젝트 전용이므로 `[Preset:]` 접두사와 프리셋 확인 문장을 **쓰지 않는다**. 플러그인으로 배포되어 여러 스택에 노출되는 가이드(원본 nextjs-* 2종)는 오작동 방지를 위해 **쓴다** | ≤450자 (description 값 기준, `name:` 행 제외) |
| 2 | `## Quick Start` — 작업 단위 체크리스트 2개 | 체크리스트 이름(New Component/New Route Handler 등)과 항목은 스택에서 도출 | 항목 6~9개/개 |
| 3 | `## Architecture Overview` | 스택 구성 요소와 책임 경계 | ≤30줄 |
| 4 | `## Directory Structure` | 해당 스택의 관례적 배치 (프로젝트 실제 구조가 있으면 그것을 우선) | ≤30줄 |
| 5 | `## Core Principles (N Key Rules)` — 번호형 규칙 + 코드 예시 | 규칙 5~8개. 각 규칙에 좋은/나쁜 예 코드 1쌍. **backend는 입력 검증·인증/권한 규칙을, frontend는 반복 UI 추출(공통 레이아웃) 규칙을 반드시 포함** — 스택이 바뀌어도 이 두 범주는 보편이다. backend의 인증/권한 규칙에는 **존재 누설 금지**를 포함한다: 리소스 부재와 권한 없음이 외부에 동일한 응답으로 보여야 한다 — 둘을 구분해 응답하면 미인가 사용자가 리소스 존재를 열거할 수 있다 (권한 메커니즘이 RLS든 정책 엔진이든 ORM 스코프든 성립) | 규칙당 ≤20줄 |
| 6 | `## Common Imports` | 스택 표준 import 블록 | ≤30줄 |
| 7 | 보조 섹션 1개 (frontend: 컴포넌트 템플릿 / backend: HTTP Status + Anti-Patterns) | 스택별 선택 | ≤40줄 |
| 8 | `## Navigation Guide` — **태스크→리소스 매핑 테이블** | "하려는 일 → 읽을 파일" 행. resources/ 전 파일이 정확히 1회 이상 등장해야 함 | 전 리소스 커버 |

## resources/ 분할 규칙

- 파일 수는 스택 복잡도가 아니라 **슬롯 수에서 도출한다**: 필수 7슬롯(병합 시 감소) +
  선택 슬롯 0~3개 = **6~10개 파일**. 6 미만은 필수 슬롯을 3회 이상 병합했을 때만 나오는데,
  병합할수록 파일이 커져 300줄 상한과 충돌하므로 권장하지 않는다
- 백엔드 유형(BaaS/자체 구축)은 **backend-guide의 선택 슬롯 수에만** 영향을 준다: BaaS 조합은
  인프라 관심사가 적어 6~7파일에 수렴하고, 자체 구축 조합은 8~10파일이 된다.
  **frontend-guide 파일 수는 백엔드 유형과 무관하다** — UI 관심사(라우팅·스타일·상태·성능·
  타입)는 백엔드가 BaaS라고 줄지 않는다
- 각 파일 ≤300줄. 초과 시 파일 상단에 TOC
- 파일명은 태스크 중심 (`api-routes.md`, `database-patterns.md`) — 기술명 나열 금지
- 데이터 액세스·인증 리소스는 **확정 조합 전용** 내용만 담는다
- **각 리소스는 해당 범주의 오용 목록을 포함한다** — "올바른 형태"만으로는 부족하다.
  두 형식이 효과적이다: ① 버전 관용구 대조표(구 습관 → 현재 형태), ② 혼동 쌍 목록(의미가
  비슷해 잘못 고르는 API·패턴과 각각의 정확한 적용 조건). 확정 스택·버전에서 실제로
  관찰되는 오용만 적는다 — 일반론적 "흔한 실수"는 쓰지 않는다

### 리소스 슬롯 표 (스택 무관 — 원본 리소스 20종에서 도출)

슬롯은 **커버리지 의무이지 파일 의무가 아니다.** 필수 슬롯마다 전용 파일을 만들거나
다른 파일에 병합한다 — 병합해도 Navigation Guide에 해당 태스크 행이 있어야 한다.
파일 수 예산(6~10)은 병합으로 지킨다. 슬롯명은 개념이며 파일명은 태스크 중심으로 짓는다.

**frontend-guide 필수 슬롯 7:**

| 슬롯 | 내용 계약 |
| --- | --- |
| 컴포넌트 패턴 | 반복 UI 추출(공통 레이아웃) 규칙 포함 — 허브 원칙의 심화. **추출 규칙에는 생성 전 탐색 의무를 함께 넣는다**: 새 공통 컴포넌트를 만들기 전에 공통 디렉토리를 검색해 기존 것을 재사용한다 — 중복의 다수는 추출 실패가 아니라 탐색 실패에서 생긴다. 공통 컴포넌트가 소유하는 디자인 토큰(높이·타이포·여백)은 그 컴포넌트 한 곳에서만 정의하고 사용처는 props로만 제어한다 |
| 데이터 페칭 | 이 스택의 표준 페칭 계층 + 컴포넌트 직접 호출 금지 경계. **경계를 강제하는 수단을 함께 제시한다** — 서버 전용 모듈에 명시적 마커를 달아 클라이언트 번들 유입을 빌드 에러로 승격시킨다. 경계가 규율로만 존재하면 조용히 깨진다: 일부 서버 코드는 클라이언트에서 import해도 에러 없이 번들되며, 이때 실패는 빌드가 아니라 런타임 또는 비밀 노출로 나타난다 |
| 라우팅 | 라우트 정의·중첩·보호 라우트 |
| 상태 관리 | 로컬/전역 구분 기준 + 선택 도구의 구독 패턴 |
| 스타일링 | 이 스택의 스타일 체계와 금지 패턴 |
| 로딩/에러 상태 | 로딩·빈·에러 3상태 처리 (컴포넌트 패턴에 병합 가능) |
| 완전 예제 | 기능 1개의 처음~끝 관통 예제 (목록+생성 흐름 권장) |

**backend-guide 필수 슬롯 7:**

| 슬롯 | 내용 계약 |
| --- | --- |
| API 엔드포인트 | 이 스택의 표준 핸들러 형태 + 요청/응답 계약 |
| 데이터 액세스 | 쿼리/클라이언트 패턴 전용 — 테이블 설계는 T1 데이터 모델링 카드 참조 행으로 (복사 금지, **참조에는 카드의 실제 경로를 적는다** — 경로 없는 참조는 도달 불가다). **변이(update/delete)는 영향 행 수를 확인하는 형태로 제시한다** — 0행 변이를 성공으로 응답하는 것이 이 계층의 대표 함정이다 |
| 입력 검증 | 검증 라이브러리 패턴 + DB 제약 이중화. **환경변수도 입력이다**: 검증된 단일 모듈을 두어 앱 코드가 환경변수를 직접 읽지 못하게 하고, 누락·형식 오류가 첫 사용 시점이 아니라 **부팅 시점에** 실패하게 한다. 서버 전용 비밀이 클라이언트 노출 접두사(`NEXT_PUBLIC_*`·`VITE_*` 등 번들에 인라인되는 이름)에 들어가지 않음을 이 모듈에서 강제하며, 공개 변수와 비밀은 스키마를 분리한다 |
| 인증/미들웨어 경계 | 인증 확인 위치·권한 경계 — 허브 보안 원칙의 심화. **권한 방어의 층수는 `pack.json`의 `dataLayerPolicyEngine`이 정한다 — 이 슬롯 계약이 정하지 않는다**: 정책 엔진이 **있으면**(RLS·행 보안) 애플리케이션 층 소유권 필터와 함께 두고 어느 한쪽도 단독 방어로 신뢰하지 않는다. **없으면**(신뢰된 연결로 붙는 자체 서버 등) 애플리케이션 층이 **유일한 경계**이며 소유권 필터 누락이 곧 데이터 유출이다 — 여기에 "데이터 계층이 백업한다"를 쓰면 정확히 반대 지침이 된다. **인증 플로우(로그인·가입·로그아웃)와 로그인 후 복귀**를 포함한다: 차단된 경로를 보존해 인증 후 되돌려 보내되 복귀 경로가 내부 경로임을 검증한다(`//host`·`/\host`·제어문자 삽입은 브라우저에서 외부 URL로 파싱된다 — 문자열 prefix 검사만으로는 부족하다). 인증 실패 응답은 일반화한다 — 실패 사유를 구분해 알리면 계정 존재 여부가 누설된다. 미인증 처리는 **응답 형식을 경로에 맞춘다**: API 경로는 인증 오류 봉투를, 페이지 경로는 리다이렉트를 반환한다 |
| 에러 처리 | 상태 코드 매핑 + 이 스택의 에러 코드표 |
| 테스트 | 이 스택의 표준 테스트 도구·패턴 |
| 완전 예제 | 엔드포인트 1개의 검증→처리→응답 관통 예제 |

**선택 슬롯** (스택 복잡도·확신도에 따라 0~3개): 파일 구성 · 성능 · 언어/타입 표준 ·
아키텍처 심화 · 프론트엔드 테스트 · 스택 고유 메커니즘(프레임워크 변이 메커니즘,
데이터 플랫폼 고유 패턴 등)

**공백 규칙**: 필수 슬롯이라도 확신 있는 패턴을 소환할 수 없으면 비운다 — 빈 슬롯이
틀린 내용보다 낫다는 원칙은 슬롯 표보다 우선한다. 단 **침묵 생략은 금지**: 생성 보고에
"공백 슬롯: <이름>"을 명시해 lessons 루프가 채울 대상으로 남긴다.

## 검증 — 생성자가 반환 전에, 메인 세션이 Step 4에서 (이중 소유)

이 규격서에서 기계로 확인 가능한 항목은 **전부 스크립트가 소유한다**(검사 목록은
`scripts/guide-gate.sh --help`). 판정은 FAIL / WARN / REVIEW 3단이고 **FAIL이 남으면
설치하지 않는다.** 기계가 판정할 수 없어 사람이 지킬 것은 둘뿐이다:

1. description이 본문에 **실재하는** 내용만 약속하는가 (placeholder 사고의 재발 방지)
2. 확신 부족으로 비운 필수 슬롯을 보고에 "공백 슬롯: <이름>"으로 명시했는가
   (**침묵 생략 = 실패**, 보고된 공백 = 통과)

## 생성 스탬프 형식

SKILL.md frontmatter 직후 1줄:

```
<!-- epcc-guide: generated YYYY-MM-DD stack=<frontend>+<backendType>+<database>+<dataAccess> pkgs=<pkg>@<major> <pkg>@<major> ... -->
```

재생성 시 이 스탬프와 파일 수정 시각을 대조해 수동 편집을 감지한다. `pkgs=`에는 가이드가
import하는 서드파티 패키지를 **빠짐없이** 싣는다 — 빠진 패키지는 버전 드리프트 검사에서
대조 대상 자체가 생기지 않아 낡음이 영영 보이지 않는다 (누락분은 게이트가 WARN으로 잡는다).

## 검증 기준선 (사전 제작 가이드 전용)

플러그인이 배포하는 **사전 제작 가이드**(생성물이 아니라 손으로 진화하는 원본)는 생성
스탬프 대신 기준선을 SKILL.md 첫머리에 1줄 둔다:

```
<!-- epcc-guide-baseline: verified YYYY-MM-DD <pkg>@<major> <pkg>@<major> ... -->
```

- 이 가이드의 지침이 **어느 메이저 버전을 전제로 검증됐는지** 선언한다
- `epcc-init`이 프로젝트의 `package.json`과 메이저 버전을 대조해, 어긋날 때만 사용자에게
  보고한다 (재생성 여부를 **묻지 않는다** — 사용자는 낡음을 판단할 근거가 없다)
- 가이드를 감사·수리할 때 `verified` 날짜와 버전 목록을 함께 갱신한다

> 이것이 부패 대응의 통로다. 실측에서 사전 제작 가이드가 폐기 API와 이전 메이저 버전
