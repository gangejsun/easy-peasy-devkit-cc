# 축 팩 리소스 구조 템플릿

**L1 저작 에이전트가 형식을 맞추기 위해 읽는 유일한 문서다.** 기존 팩 5개
(`nextjs` · `react-vite` · `vue` · `supabase` · `aws-container`)에서 한 번 추출했다.

> **다른 팩·가이드를 열지 않는다.** 이전 규격은 "형식 참조만, 내용 복사 금지"라는
> 방화벽을 지시로 걸었고 **실측(2026-08-23)에서 실패했다** — 깨진 `safeReturnTo`가
> react-vite 팩에서 vue 팩으로 그대로 복사됐고, 같은 결함이 출하본 네 곳 전부에
> 있었다. 지시로는 막히지 않는다. 형식은 이 문서가 주고, 내용은 스택 지식에서 온다.
>
> 이 문서가 병렬 저작의 공통 기준이기도 하다. 클러스터를 갈라 쓰면 어조·밀도·표기가
> 갈리는데, 그것을 붙잡는 것이 여기다.

## 1. 파일 머리

```
<!-- epcc-pack: <axis>/<pack> v<버전> -->
# <파일 주제> — <한 줄 부제>

<도입 1~3줄. 이 파일이 무엇을 소유하고 무엇을 소유하지 않는지.>
```

소유하지 않는 것이 있으면 **어디가 소유하는지 경로로** 적는다. 경로 없는 참조는
도달 불가다. 이음매의 몫이면 그렇게 명시한다 — 팩이 비어 보이는 것과 이음매가
채울 자리는 다르다.

## 2. 절 골격

**번호형 `## N. 제목` 을 쓴다.** 파일이 소유하는 코드 파일이 있으면 제목에 경로를 단다.

```
## 1. 결정 트리
## 2. 스토어 작성 (`src/stores/uiStore.ts`)
## 3. 구독 — `storeToRefs`가 필수다
...
## 오용 목록 ① — <구 도구/버전> → <현재> 관용구 대조표
## 오용 목록 ② — 혼동 쌍
```

- 본문 절 6~9개. 마지막 두 절은 **항상 오용 목록**이다 (규격서의 오용 의무)
- 첫 절은 **판단**이다: 결정 트리 · 판단 기준표 · 클라이언트 매트릭스처럼
  "무엇을 언제 고르는가". 방법보다 선택이 먼저다
- **산문은 한국어로 쓴다.** 코드·식별자·표 헤더의 기술 용어는 원어 그대로 둔다
  (`supabase` 팩이 영어 산문인 것은 드리프트다 — 따라 하지 않는다)
  - 이건 **이 저장소의 팩 저술 규약**이지 소비자 출력 규범이 아니다. 팩 리소스는 모델이 읽는
    자산이라 프로젝트의 응답 언어(T0 「언어」)를 따르지 않는다 — 둘은 다른 층이다

## 3. 오용 목록 두 형식

규격서가 요구하는 두 형식이고 표 헤더까지 고정한다.

```markdown
## 오용 목록 ① — Vuex → Pinia 관용구 대조표

| 구 습관 (Vuex) | 현재 형태 (Pinia) |
| --- | --- |
| `mutations`로만 상태 변경 | 액션에서 직접 대입 |

## 오용 목록 ② — 혼동 쌍

| 자주 잘못 고르는 것 | 정확한 적용 조건 |
| --- | --- |
| `storeToRefs` vs 구조 분해 | 상태·getter는 앞, 액션은 뒤 |
```

**확정 스택·버전에서 실제로 관찰되는 오용만 적는다.** 일반론적 "흔한 실수"는 쓰지 않는다.

## 4. 좋은/나쁜 예 표기 — 게이트가 읽는 규약이다

게이트의 `codelines()`가 이 표기로 안티패턴 구간을 제외한다. 어기면 **팩이 자기
정책 위반으로 잡힌다**(자기 나쁜 예에 걸린다).

| 상황 | 표기 |
| --- | --- |
| `//`·`#`·`--` 주석을 쓰는 언어 | 펜스 **안** 주석 행에 `// ❌` / `// ✅` |
| `.vue`·HTML·JSX 마크업 펜스 | **펜스 바로 앞 산문 행에 ❌** |

두 번째가 중요하다. `codelines()`가 인정하는 주석 접두사는 `//` · `#` · `*` · `--`
뿐이라 **HTML 주석(`<!-- ❌ -->`)은 코드 행으로 세어진다.** 마크업 펜스의 나쁜 예는
반드시 펜스 앞 산문에 ❌를 둔다.

식별자에 `BAD`·`Good`이 들어가는 것(`BAD_SHAPE`·`BAD_REQUEST`)은 표식이 아니다 —
게이트가 단어 경계에서 `_`와 숫자를 빼서 구분하지만, 표식은 `❌`/`✅`를 쓰는 것이 안전하다.

## 5. 코드 파일 표시 — 실행 검증의 입력이다

표시가 **두 가지**다. 섞으면 `pack-smoke.sh`가 발췌를 완전한 파일로 오인해 위양성을 낸다.

| 표시 | 뜻 | pack-smoke의 처리 |
| --- | --- | --- |
| 펜스 첫 줄 `// src/foo.ts` | **라벨** — 이 조각이 어느 파일의 것인지 알린다 | 복원은 하되 구문·타입 검사는 걸지 않는다 |
| 펜스 앞 줄 `<!-- file: src/foo.ts -->` | **완전 파일 주장** — 이 펜스만으로 그 파일이다 | 구문·타입 검사 대상 |

```markdown
<!-- file: src/lib/safeReturnTo.ts -->
```ts
// src/lib/safeReturnTo.ts
export function safeReturnTo(raw: unknown, fallback = '/tasks'): string {
  ...
}
```
```

- **`<!-- file: -->`는 다음 세 부류에 반드시 단다**: 보안 원시함수 · 설정 파일 ·
  테스트 하네스. 실측에서 실행으로 잡힌 결함이 전부 여기였다 (복귀 경로 검증 ·
  msw 핸들러 · vite 설정 · 마운트 하네스)
- 설정의 일부만 보이는 관용구(`resolve: { alias: ... }`)는 **라벨**이다.
  완전 파일로 주장하면 조각으로 판정돼 경고가 난다
- 같은 경로를 여러 펜스가 주장해도 **이어 붙이지 않는다** — 펜스마다 독립 단위다
- 보안 벡터 시험은 두 표시 **모두**에서 함수를 찾는다. 라벨만 달아도 벡터는 돌아간다

## 6. 밀도와 예산

| 항목 | 목표 |
| --- | --- |
| 파일 | ≤300줄 (게이트 FAIL) · 290줄 초과부터 WARN |
| 절 하나 | 20~40줄 |
| 코드 펜스 | 절마다 1~2개, 각 5~25줄 |
| 산문 : 코드 | 대략 1 : 1.5 — 코드만 있으면 언제 쓰는지가 없고, 산문만 있으면 못 쓴다 |

**예산 상한에 붙이지 않는다.** 300줄에 도달한 파일은 다음 변경 때 저자가 아니라
예산이 삭제 대상을 고른다.

## 7. 어조

- 검증 가능한 사실만 **단정형**으로 쓴다. 확신이 없으면 쓰지 않는다 —
  **빈 슬롯이 틀린 내용보다 낫다** (비웠으면 보고에 "공백 슬롯"으로 명시한다)
- "왜"를 한 줄로 붙인다. 규칙만 있으면 지켜지지 않고, 근거가 있으면 응용된다
- 실측으로 확인한 것은 그렇게 적는다 ("실행 확인" · "실측에서")
- **버전 주장은 태그한다** — `vN에서 추가/제거` · `이제는` · `더 이상` 류를 쓰면
  같은 줄이나 바로 앞 줄에 `<!-- verified: <근거> -->` 또는 `<!-- unverified -->`를
  단다. 게이트가 태그 없는 주장을 WARN으로 모아 감사 B에 넘긴다.
  실측에서 이 부류 5건이 거짓이었다 — 모델은 자기가 틀렸다는 것을 모른다
  - **태그는 같은 줄에 단다.** 앞 줄 귀속은 그 줄이 **태그만 있는 독립 주석**일 때만
    인정된다. 표 안에서는 마지막 셀 안에 넣는다 — 표 사이에 주석 줄을 넣으면 표가 깨진다.
    태그 하나가 뒤따르는 표 행 전부를 덮으면 **미태그 주장이 검사를 통과하면서 검사를 피한다**
  - **한국어 산문의 「(실행 확인)」도 주장이다.** 게이트가 수집하지만, 근거를 함께 적는
    태그가 낫다. 실측에서 **거짓 4건 중 3건이 미태그 「(실행 확인)」 블록에 몰려 있었다** —
    태그 규율이 도달하지 못한 곳에서만 결함이 살아남았다

## 7-B. 순환 검증 금지 — 「실행 확인」이 검증이 아닌 경우

**네가 만든 픽스처에 네가 넣은 값을 네가 읽는 것은 검증이 아니다.**

실측(2026-08-23): 한 저자가 Prisma `P2025`의 `meta.cause` 문구를 「실행 확인」으로 태그했는데,
그 문구는 **자기가 손으로 만든 에러 객체에 자기가 넣은 값**이었다. 실제 라이브러리가 만드는
값은 달랐고 감사가 그것을 잡았다. 저자의 자기 신고: *"그것을 실행 확인이라 표시한 것은
순환 검증이었다."*

| 검증인 것 | 검증이 아닌 것 |
| --- | --- |
| 라이브러리·런타임이 **스스로 만든** 값을 읽었다 | 내가 구성한 객체의 필드를 다시 읽었다 |
| 설치본의 `.d.ts`·소스를 행 번호까지 대조했다 | 기억하는 API 형태를 그럴듯하게 적었다 |
| 실제 요청·프로세스·DB가 만든 출력을 계측했다 | 스텁이 내 기대대로 반응했다 |

스텁이 필요한 것은 정상이다(이음매 심볼은 팩만으로 해소되지 않는다). **스텁으로 확인한
것과 실물로 확인한 것을 태그에서 구분하라** — `<!-- verified: 스텁으로 배선만 확인,
실물 미검증 -->`처럼 범위를 적는다. 태그가 **확인 범위를 넘어 미확인 영역의 성질까지
주장하면** 그것이 거짓의 전형이다.

## 7-C. 테스트를 실으면 차단을 증명한다

**부정 단언만 있는 테스트는 차단 장치가 아니다.**

실측: 「이 축에서 가장 비싼 테스트」로 제시된 소유권 회귀 테스트가 `expect(404)`만 걸어,
쿼리 함수를 통째로 `return null`로 바꿔도 초록이었다 — **모든 것이 404이기 때문이다.**

```ts
// ❌ 구현을 통째로 실패시켜도 통과한다
it('남의 것을 읽으면 404다', async () => {
  expect((await get(other.id)).status).toBe(404);
});
```

긍정 경로를 **같은 `it` 안에 짝으로** 건다 — 소유자가 자기 것에 200을 받는다는 단언이
있어야 404가 "차단"인지 "전부 고장"인지 갈린다. 게이트의 `check_blocking_proof`가
실패 단언만 있는 테스트 파일을 REVIEW로 올린다.

## 8. 보안 원시함수는 여기서 예외다

경로 검증 · 토큰 비교 · 이스케이프 · 리다이렉트 검증은 **형식만이 아니라 내용도
새로 쓴다.** `assets/security-vectors.md`의 해당 벡터를 네 구현에 실제로 통과시키고
결과를 반환 데이터에 싣는다. 게이트의 `check_security_shapes`가 알려진 취약 형태
두 가지를 FAIL로 막지만, **막는 것은 이미 아는 형태뿐**이다.
