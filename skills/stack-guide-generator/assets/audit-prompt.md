grep으로 확정"하는 절단면 검사법을 수행할 수 있는 것은 C뿐이다.
**세 감사의 경계에 걸친 것도 C의 명시 담당이다** — 정책이 선언한 것과 리소스가 실제로
하는 것의 불일치가 그 자리다 (실측 57건 중 26건이 이 부류).

3분할하는 이유는 실측이다: 감사 1개가 1,946줄을 전수로 읽어 20분이었고, 실제로 결함을
잡은 세 경로가 서로 독립적이었다. 최대 발견(오픈 리다이렉트)은 A에, 거짓 버전 주장 5건은
B에 온전히 들어간다 — 갈라도 손실이 없다.

## 감사 규율

- **너의 임무는 "잘 됐다"가 아니라 "무엇이 틀렸나"를 찾는 것이다.** 결함 0건 보고는
  결함이 없을 때만 정당하다 — 찾지 못한 것과 없는 것은 다르다
- **틀린 지침은 없는 지침보다 나쁘다.** 정확성 의심 항목은 적극적으로 제기하라
- **분량 편향 금지.** 길다고 좋은 게 아니다. 실무에서 코드를 쓸 때 실제로 실수를
  막아주는 지침의 밀도로 판단한다
- 확신도를 구분해 보고하라: **확정**(근거로 단정 가능) / **의심**(검증 필요)
- 모든 지적에 `파일:줄`과 근거를 붙인다. 근거 없는 지적은 보고하지 않는다

## 검사 축

아래 5축은 셋으로 나뉜다. **네 담당이 아닌 축은 보지 않는다** — 셋이 같은 것을 세면
병렬의 이득이 사라진다.

**1. 정확성 (감사 B)** — 확정 스택의 **현재 버전** 기준으로 틀리거나 낡은 지침.

**넘겨받은 버전 주장 인벤토리를 한 줄씩 판정하는 것이 감사 B의 전부다** (참 / 거짓 /
확인 불가, 거짓이면 정확한 서술). **가능하면 실행으로 판정하라** — 실측에서 거짓 5건이
전부 실행으로 드러났다. 이 부류는 생성 규율로 막을 수 없어 — 모델은 자기가 틀렸다는 것을
모르므로 잘못 확신한 항목도 '확정'으로 쓴다 — 여기가 감사의 고유 영역이다.

**태그가 붙었다는 것은 "저자가 주장했다"는 선언이지 "참"이라는 증명이 아니다.**
`<!-- verified: ... -->`의 근거 문구까지 의심하라 — 근거가 실제로 그 주장을 지지하는가.

**특히 순환 검증을 찾아라.** 실측(2026-08-23)에서 저자가 「실행 확인」으로 태그한 문구가
**자기가 손으로 만든 에러 객체에 자기가 넣은 값**이었다. 라이브러리가 스스로 만든 값이
아니면 검증이 아니다. 태그의 근거가 어느 쪽인지 가려라:

| 검증 | 순환 |
| --- | --- |
| 라이브러리·런타임이 스스로 만든 값 | 저자가 구성한 객체의 필드 |
| 설치본 소스를 행 번호까지 대조 | 기억하는 API 형태 |
| 실제 요청·프로세스·DB의 출력 | 스텁이 기대대로 반응함 |

그리고 **태그가 확인 범위를 넘는 것**을 잡아라 — "각주가 붙은 행만 확인했고 나머지는
폐기가 아니다"처럼 확인하지 않은 영역의 성질까지 단정하는 형태가 이 부류의 전형이다.

**인벤토리는 게이트가 전수 수집하지만 사각지대가 있다.** 인벤토리에 없는데 본문에서
발견한 주장이 있으면 **추가로 판정하고 그 사실을 밝혀라** — 기계 스캔의 구멍을 드러내는
것도 네 산출이다.

**2. 자기모순 (감사 C)** — 같은 팩·스킬 안에서 서로 어긋나는 서술.
허브(SKILL.md) 규칙 vs 리소스의 상세 / 선언한 규율 vs 실제 예시 코드 / 파일마다 다른
디렉토리 구조·파일명 규칙·함수 시그니처·도메인 어휘.

**3. 절단면 (감사 C가 전수 · 감사 A는 실행으로 확인되는 것만)** — 짝이 맞지 않는 조각. **이 축은 기계 게이트가 잡지 못한다**(가이드는 원래
라이브러리 API와 발췌 조각을 담으므로 블라인드 스캔은 위양성투성이다). 네가 잡아야 한다.

찾는 방법: 먼저 전문을 읽으며 **의심 이름을 모으고**, 각 이름에 `grep -rn '<이름>' <가이드>`를
실행해 정의와 호출이 모두 존재하는지 확인한다 — 읽기로 후보를 좁히고 grep으로 확정한다.

- 정의 없이 호출되는 프로젝트 로컬 함수·훅 (라이브러리 API는 해당 없음)
- 정의만 있고 아무도 쓰지 않는 유령 항목 (선언된 쿼리 파라미터·필드·컴포넌트)
- 그대로 복사하면 컴파일되지 않는 예시 (컴포넌트 래퍼 없이 최상위에 놓인 훅 호출 등)
- 이름만 언급되고 방법이 없는 개념 ("X를 쓰라"고 하고 예시가 없는 것)
- 한 파일에서 지운 것의 참조가 다른 파일에 남은 흔적

**4. 보안 (감사 A)** — 인증·권한·비밀 관련 주장은 **전부** 검증한다.
**읽지 말고 돌려라.** `assets/security-vectors.md`의 벡터 중 `pack-smoke.sh`가 자동
실행하지 못한 부류(경로 정규화 · 토큰 비교 · 이스케이프 · 인가 판정)를 직접 돌린다.
실측에서 세 번의 감사가 읽기로 놓친 오픈 리다이렉트를 네 번째 감사가 **실행으로** 찾았다.
권한 판정의 근거를 사용자가 수정할 수 있는 곳에서 읽는가 / 리소스 부재와 권한 없음을
구분해 응답해 존재를 누설하는가 / 리다이렉트·콜백 경로 검증이 실제로 우회 불가능한가 /
서버 전용 비밀이 클라이언트에 노출되는 경로가 있는가 / 변이가 소유권을 확인하는가.

**4-B. 차단 증명 (감사 C)** — 팩이 「차단 장치」로 제시한 것이 실제로 차단을 증명하는가.
실측에서 소유권 회귀 테스트가 `expect(404)`만 걸어, 쿼리 함수를 통째로 `return null`로
바꿔도 초록이었다 — **모든 것이 404이기 때문이다.** 부정 단언만 있는 테스트, 정규식이
자기 예도 못 잡는 정책, 픽스처가 없는 규칙을 찾아라.

**5. 슬롯 계약 이행 (감사 C)** — 규격서의 필수 슬롯이 **이름만이 아니라 내용 계약대로** 채워졌는가.
비어 있다면 생성 보고에 공백으로 명시됐는가(침묵 생략 = 결함).

## 반환 형식 (최종 텍스트 = 데이터, 사람용 인사말 불필요)

1. **결함 목록** — 축별로, 각 항목에 `파일:줄` · 확정/의심 · 심각도(치명/높음/보통/낮음) ·
   근거 · 권장 수리 방향
2. **슬롯 계약 이행표** — 필수 슬롯별 이행/부분/미이행 + 위치
3. **버전 주장 판정표** — 주장 원문 · `파일:줄` · 참/거짓/확인 불가 · 거짓이면 정확한 서술
4. **총평 2문장** — 이 가이드를 그대로 설치해도 되는가
5. **미검사로 남긴 것** — 돌리지 못한 벡터·검사와 그 이유. **침묵 생략은 금지다**:
   "검사했는데 깨끗함"과 "검사하지 않음"이 구분되지 않으면 보고가 거짓이 된다
