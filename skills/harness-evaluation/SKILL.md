# Harness(Graph) Evaluation

자산 단위("무엇이 있는가")가 아니라 **경로 단위**("작업 1건이 어떤 노드를 밟고,
어디서 멈추고, 무엇을 남기는가")로 평가한다. 점수는 내지 않는다 —
산출물은 **결함 목록**이고, 그 자체가 개선 백로그다.

## 7축

**축 간 담당이 겹치면 결과가 애매해진다.** 각 축의 "만 본다"를 지킨다.

| 축 | 질문 | 기계 판정 (Step 1) | 모델 판단 (Step 2) |
| --- | --- | --- | --- |
| **P1 라우팅·정본 일관성** | 같은 사실을 두 곳이 다르게 주장하지 않는가 | S/M/L grep(취약점 등급표는 오탐이므로 제외) · `--graph`의 Phase 대조 · `--fast`의 버전 스탬프·`shared-copy` | 위반이 실제 오동작을 만드는가 · 문서 의존성 6엣지 폐쇄 · 참조 신선도 4축 |
| **P2 발동 정확성** | ①조건 충족 시 발동하는가 ②노드 권한 형태가 맞는가 ③잡아야 할 것을 잡는가 **④안 잡을 것을 안 잡는가** | 그래프 선언 대조 · 에이전트 frontmatter · `--self-test` 양성/무해 픽스처 | 수동이 의도인가 누락인가 · 게이트 미탐 · handoff 복원 충분성 · 게이트가 전제하는 검증 기반 실재 · **오탐 이력**(`--lessons`의 `false-positive`) |
| **P3 루프 종료성** | 반복 노드가 상한·종료 술어를 갖는가 | 상한 grep — **references/ 포함** | 상한이 작업 성격에 적정한가 |
| **P4 되먹임 폐쇄성** | 기록이 자산 diff로 돌아오는가 | `--lessons` 승격 후보 + `--graph`의 저장소 소비 경로 | 승격 형태(훅/스킬/규칙) 선택이 옳은가 · **수축이 일어나는가** |
| **P5 경로 비용** | 대표 작업 1건의 노드·게이트 수와 상주 비용이 적정한가 | `--usage`(상주 컨텍스트 비용 · graph.log · skilluse.log) | Reversible 경로의 과잉 게이트 · 상주 예산 배분 |
| **P6 구조 절제** | ①**과잉** ②**중복** ③**애매** (아래 표) | `--usage` 무호출 목록 · `--fast` 네이티브 문구·description 위생 · 잔존 경고 | 각 항목의 실질 판단 |
| **P7 경계** | ①밖으로 나가는가 ②남는가 ③출처가 있는가 | `--fast`의 platform-contract 180일 · 로그 회전 grep | 사전 고지 지점 실재 · 잔존물의 비밀정보 · 귀속 |

**P5와 P6은 직교한다** — 비용이 싸도 중복일 수 있고(안 쓰이는 스킬), 비싸도 정당할 수
있다(security-check). P2와 P7도 직교한다 — **P2는 차단력, P7은 경계 넘김**.

### P6 세부 — 이미 있는 자산에게 다시 던지는 3-질문

`rules/harness-change.md`의 추가 전 3-질문과 해결 수단 우선순위는 **자산을 만들 때만**
걸린다. 존재하는 자산에게 그 질문을 다시 던지는 곳이 여기다. 없으면 하네스는 자라기만 한다.

| 항목 | 무엇을 보는가 |
| --- | --- |
| ① **과잉** | 지금도 필요한가 · 모델 향상으로 불필요해지지 않았는가 · 문서 1~3줄로 될 것을 스크립트로 만들지 않았는가(해결 수단 우선순위 역행) |
| ② **중복** | 역할이 겹치는 자산 쌍 — 커스텀 vs **네이티브**(`/code-review`·`/simplify`·`/security-review`·`skill-creator`·`/init`·`/run`·`/loop`) · 커스텀 vs 커스텀 · 같은 규범을 두 파일이 주장(정본/인용 미표시) |
| ③ **애매** | 산출이 행동으로 이어지는가 — **꺼지지 않는 경고** · 판정 불가를 차단으로 접음 · 두 검사가 같은 것을 셈 · 조치 문구 없는 실패 보고 |

판정에는 시점 스탬프("Claude Code 버전 · 모델 · 날짜")를 반드시 남기고, 직전 스탬프가
30일 이내면 재조사를 생략한다. **커스텀 폐기를 제안하려면 양쪽 본문을 실제로 열어**
커버 영역을 비교한다 — 네이티브의 존재는 중복의 증거이지 열등의 증거가 아니다.
비교 대상은 **훼손되지 않은 최선 버전**이어야 한다(과거 커밋이 내용을 삭감했을 수 있다).

#### P6-②의 판정은 셋이다 — 대체 · 유지 · 합성

한 축만 보고 판정하지 않는다. **다섯 관점을 모두 적고** 판정한다.

| 관점 | 무엇을 보는가 |
| --- | --- |
| 커버 영역 | 한쪽만 다루는 영역이 실재하는가 (양쪽 본문을 연 뒤에만 적는다) |
| 발동 정확성 | 미탐·오탐 이력 — `--lessons`의 `false-positive`, `--self-test` 픽스처 |
| 유지비 | 우리가 계속 고쳐야 하는가, 플랫폼이 고쳐 주는가 |
| 소비자 도달 | 설치 없이 모든 사용자에게 닿는가 |
| 모델 의존성 | 모델이 좋아지면 저절로 불필요해지는 성질인가 |

| 판정 | 조건 | 적용 |
| --- | --- | --- |
| **네이티브로 대체** | 다섯 관점에서 네이티브가 동등 이상 | 커스텀 폐기(폐기 프로토콜). 남은 참조를 네이티브 호출로 바꾼다 |
| **커스텀 유지** | 네이티브가 못 다루는 영역이 실재 | 그 영역을 스킬 본문에 1~2줄로 남긴다 — 다음 평가가 같은 질문을 다시 던진다 |
| **합성** | 관점별로 우열이 갈림 | **네이티브를 기반에 두고 커스텀의 고유 가치만 얇게 올린다.** 커스텀이 네이티브를 재구현하지 않는다 |

합성의 형태는 하나다 — **네이티브를 호출하고, 그 산출에 우리 고유의 것만 더한다.**
선례: `/security-review`(브랜치 diff·네이티브)와 `security-review` 스킬(전수 감사·의존성
CVE·시크릿·결제)은 커버가 겹치지 않게 갈라져 둘 다 살아남았고, `receiving-code-review`는
지적을 *생성*하지 않고 *검증*하는 쪽으로 좁혀 네이티브 위에 얹혔다.

**적용까지가 판정이다.** 결함 목록에 머물면 하네스는 바뀌지 않는다 — 그래프의
`eval-report → rule-promotion`(자산 교체·승격)과 `eval-report → skill-enhancer`(스킬 재설계)가
그 경로이고, 판정마다 둘 중 어느 쪽으로 보내는지 적는다.

## 워크플로우

### Step 1: 기계 판정 수집 — 다시 세지 않는다

```bash
bash "${CLAUDE_PLUGIN_ROOT:-.}/scripts/doctor.sh" --all
bash "${CLAUDE_PLUGIN_ROOT:-.}/scripts/doctor.sh" --usage --root <소비자 프로젝트>  # 있을 때만
# P1 — 라우팅 어휘 (심각도 등급표 문맥은 제외하고 해석)
grep -rn 'Small\|Medium\|Large' skills/*/SKILL.md
# P3 — 반복 상한 (공유 파일 포함)
grep -rln '최대 [0-9]회\|1회 재' skills/*/SKILL.md skills/*/references/*.md
# P7-① — 밖으로 나가는 노드 · P7-② — 잔존물
grep -rln 'WebSearch\|WebFetch\|codex\|gemini' skills/*/SKILL.md agents/*.md
ls dev/handoff/ 2>/dev/null | wc -l
```

**반복 증거의 출처** (P6-①·P2-④가 이것을 요구한다):
`docs/lessons.md` · `.claude/.epcc/{hookrun,graph,skilluse}.log` · `dev/handoff/*.md` ·
`dev/docs/skill-review/*` · 소비자 프로젝트(`--root`).
**2회 이상 관측된 것만 개입 근거가 된다** — 1회는 가설이지 패턴이 아니다.

### Step 2: 7축 판정 + 결함 목록

- 축마다 두 줄로 판정한다: `측정: <기계 출력 요약>` / `판정: <충족|부분 충족|미달|미계측> — <근거>`
- 결함은 `ID | 심각도 | 파일:행 | 실패 시나리오 | 개입 지점 | 수정 방향` 형식.
  심각도는 epcc-reviewer와 동일 어휘(Critical/Important/Suggestion).
- **개입 지점**은 수정이 놓일 자리다: ①시작 브리핑(T0·session-brief) ②결정 시점
  (규칙 `paths:`·스킬 발동) ③행동 체크포인트(PreToolUse) ④사후 복구(Stop·PostToolUse·handoff).
  같은 실패라도 어느 지점에 놓느냐로 효과가 갈린다.
- **Critical은 재현으로 뒷받침돼야 한다** — 픽스처·실행으로 확인한 것만. 문서 독해만으로는
  Important 이하다.
- **실패 시나리오를 쓸 수 없으면 그 결함은 보고하지 않는다** — "~일 수 있다"는 추측이다.
- **grep·doctor에 걸리지 않은 문서를 읽으러 가지 않는다.** 전 문서 독해는 폐기된 방식이다.
- 전회 판정을 계승하지 않는다 — 반드시 현재 파일로 재확인한다.

### Step 3: 저장 + 전회 대비

1. 형식: `assets/report-template.md`
2. 버전: `ls dev/docs/harness-evaluation/`의 최대 vN에 +1 (**파일명이 원장이다**)
3. 저장: `dev/docs/harness-evaluation/v{N}.md`
   — 저장 시점이 곧 외부 변화 점검 스탬프다. `session-brief` 훅이 최신 리포트의
   mtime으로 30일 경과를 계산해 다음 점검을 알린다 (별도 스탬프 파일 없음).
4. 전회가 있으면 결함 증감과 상주 비용 증감만 요약한다. 점수 추세는 없다.
5. **수축 제안을 최소 1건 검토한다.** 없으면 "없음 + 근거"를 적는다 —
   승격만 있고 수축이 없으면 하네스는 자라기만 한다.

## 부록: 커버리지 맵 (v2 10축 → v3 5축 → 7축)

축 개편 시 이 맵의 갱신이 의무다. **행선지가 빈 항목이 생기면 개편은 미완성이다.**

| 구축 (v2) | v3 행선지 | 현재 행선지 |
| --- | --- | --- |
| 1 진입 규율 | P5 + P2-① | 동일 |
| 2 토큰 효율 | P5 | P5 — `--usage` 상주 비용으로 **실측화** |
| 3 확인 편향 방지 | P2-①② | 동일 |
| 4 컨텍스트 연속성 | P4 + P2-③ | 동일 |
| 5 점진적 거버넌스 | P1 + P5 | 동일 |
| 6 자기 개선 | P4 | P4 — 승격 + **수축** |
| 7 보안 | P2-③ | P2-③(차단력) + **P7**(경계 넘김) |
| 8 네이티브 중복 | P2·P5 **판단 입력** | **P6-② 항목으로 환원** |

> 세지 않는다. 이것은 항목의 값어치 문제가 아니라 배치 문제였다.
